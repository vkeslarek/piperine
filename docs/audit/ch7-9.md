## Chapter 7 — Mixed signal

The grammar layer is largely faithful to Annex A's `connectrules_declaration`
and the `connect <disc>, <disc> [; | { stmts }]` rule form (§7.7.2) — both
parse correctly (`grammar/item.rs:1086-1121`). `connectmodule` as a module
kind is a first-class `ModuleKind` variant, distinct from `module`/
`macromodule`.

The real gap is semantic, not syntactic, and it is a single-point failure:
**`ResolveDisciplines` (§7.4/Annex F, `disciplines.rs`) unconditionally
treats any discipline mismatch across an instance port as a hard elaboration
error, one pass before `InsertConnectModules` (§7.4.4.3/§7.5-7.8,
`connect.rs`) gets a chance to check whether a registered `connectrules`
block could have bridged that exact pair.** This is not a subtle ordering
bug — `passes.rs`'s own doc comment (lines 38-47) and `connect.rs`'s own
module doc (lines 1-42) both already document it explicitly as a carried-
forward SPEC_DEVIATION, and `connect.rs`'s test suite proves the *selection
algorithm itself* is correct by constructing `Design`/`Elaborator` state by
hand, bypassing `ResolveDisciplines` entirely (`connect.rs:319-368`,
explicitly commented "bypassing `ResolveDisciplines` — see this module's own
scope-note doc comment for why that pass would otherwise veto the scenario
first"). I independently re-derived the same conclusion by reading
`disciplines.rs:99-133`'s `resolve_one_round`: the `Some(d) if d !=
callee_disc` arm at line 118 raises `DisciplineResolutionFailed` (E4003)
unconditionally — it has no knowledge of `elab.syms.connectrules` at all, and
nothing before it in `resolve_one_round` checks eligibility first. So the
claim is confirmed precisely: **every genuine discipline-crossing connection
in real `.vams` source dies at E4003 during `ResolveDisciplines`, and
`InsertConnectModules`'s E4005-producing selection logic — while itself
correct — is unreachable dead code for any input that would actually need
it.**

Beyond that headline finding, the rest of ch.7's machinery for actually
*using* a `connectmodule` productively is largely absent: `connect_mode`
(§7.7.4, `merged`/`split` semantics, §7.8.3) is a reserved word with no
grammar or elaboration support at all (only an error-message string
mentions it by name); `resolveto` (§7.4.4.3) is likewise a bare keyword with
a doc comment acknowledging it as future work; and the entire §9.22/§9.23
driver-access system function/task family (`$driver_count`, `$driver_state`,
`$driver_strength`, `driver_update`, `$driver_delay`, `$driver_next_state`,
`$driver_next_strength`, `$driver_type`) that a `connectmodule` body needs to
actually *resolve competing drivers* — arguably the entire point of
`connectmodule` per §7.6 — has zero implementation anywhere in the tree.

## Chapter 8 — Scheduling semantics

The production digital scheduler (`digital/scheduler.rs`, `DigitalState::
evaluate_until_stable`/`evaluate_dag_ordered`) implements a two-phase
delta-cycle model that gets the specific register-commit-before-comb-
reevaluate case right, but it is **not** LRM §8.3's four-region stratified
model. The four-region primitive that *would* deliver that — `Region::
{Active, Inactive, Nba, Monitor}` plus the `RegionQueue` priority scheduler
in `digital/regions.rs` — exists, is well-tested, and correctly proves the
priority-ordering and blocking-vs-NBA race-resolution rules in isolation
(§8.3's canonical example, reproduced almost verbatim in
`regions.rs:195-236`). But it has exactly one call site anywhere in the
crate outside its own file and test module: a bare `pub use` re-export in
`abi.rs:40`. **It is never invoked by the live scheduler.** Its own doc
comment says so outright. This means: `Inactive` (`#0` same-timestep
deferral) and `Monitor` (`$monitor`/`$strobe`, settled-value-only reads)
have no production implementation at all, on top of `$monitor`/`$strobe`
independently not executing anything per the ch.9 findings above.

Compounding this: gate primitives (`kernel/digital/gates.rs`) and UDPs
(`kernel/digital/udp.rs`) — the constructs §8.5.3.5 explicitly calls out for
switch/transistor-style scheduling treatment — are likewise never called
from `kernel/digital/compile.rs` (the actual digital-body compiler) or
`device/digital.rs` (the runtime element). They compile and unit-test in
isolation but never participate in a real simulated circuit's event
schedule.

The mixed-signal A2D/D2A boundary itself (§8.4.1-8.4.5) fares better — real
references exist across `core/element.rs`, `analyses/{dc,transient}.rs`,
`digital/interface.rs`, `kernel/digital/{layout,abi}.rs`, and
`flatten/analog.rs`, consistent with CLAUDE.md's claim that mixed-signal DC/
transient coupling works — but the specific `absdelta`-interpolated-event
refinement (§8.4.6) is entirely absent, and no code names or documents
§8.4.4/§8.4.5's synchronization algorithm specifically (the coupling clearly
does *something* correct-enough to pass ngspice-parity tests, but not
traceably *this* named algorithm).

## Chapter 9 — System tasks and functions

Two very different stories coexist under one chapter number. The **analog
kernel query functions** (`$temperature`, `$vt`, `$simparam`, `$simparam$str`,
`$bound_step`, `$limit`) are implemented directly in the codegen analog-
expression JIT emitter (`emit/analog_expr.rs`) and the analog kernel/device
capability files (`kernel/analog/limits.rs`, `device/analog/limits.rs`,
`kernel/analog/compile.rs`), and are genuinely live at simulation runtime —
this matches CLAUDE.md's own "known gaps" list, which correctly does not
flag these as gaps.

The **general display/diagnostic/control task family** (§9.2, §9.4, §9.7,
and everything eval/tasks.rs actually implements) is a different story
entirely. `eval/tasks.rs`'s own module doc states plainly, unprompted, that
"nothing in piperine-lang's elaboration pipeline lowers a `$`-task call into
the POM yet" as of when it was written — I traced the *current* state past
that point and found it only partially superseded: `Stmt::TaskCall` **is**
now carried through the POM unchanged and **is** pattern-matched in
codegen's flatten stage (`flatten/analog.rs:536-567` for analog bodies,
`emit/stmt.rs:105-109` for digital bodies). But the trace dead-ends at two
different points depending on domain:

- **Digital bodies**: `emit/stmt.rs:105-109` matches the display-family names
  and returns `Ok(())` — a hard no-op at JIT-emission time. Nothing is ever
  recorded. This is the *first* point at which the chain breaks for the
  digital side.
- **Analog bodies**: `flatten/analog.rs` does build a structured
  `FlatDiagnostic{severity, format}` and thread it through to the compiled
  `AnalogKernel` (`kernel/analog/compile.rs:905,986`), which exposes it via
  a public `diagnostics()` getter (`kernel/analog/kernel.rs:693-695`). This
  is real, tested plumbing — but that getter has **zero callers** anywhere
  in `piperine-codegen`, `piperine-api`, or `piperine-solver` (confirmed by
  exhaustive grep). This is the *second*, later point at which the chain
  breaks: the data is computed and stored but never read by anything that
  would print it during a real `Session`/`LiveSession` run.

Making this worse, the one integration test that should catch this — 
`crates/piperine-lang/tests/system_task_migration_completeness.rs`, whose
own header claims it proves `$write/$strobe/$display/...` "still resolve"
post-migration — is currently **entirely broken**: all 12 of its tests fail
with a parse error, because the fixture source is written in dead PHDL-era
syntax (`mod Top() {} digital Top { ... }`) that the VAMS-only grammar
(post-T46) rejects before the task-call machinery is ever exercised. This
was verified live: `cargo test -p piperine-lang --test
system_task_migration_completeness` → 0 passed, 12 failed. So on this
branch there is currently no integration-level evidence, passing or
failing-informatively, that any ch.9 system task elaborates through real
`.vams` source at all — only `eval/tasks.rs`'s own unit tests, which never
touch `parse_and_elaborate` or codegen.

Finally, by name-coverage alone, `SystemTasks::TABLE` implements 20 of
roughly 50 ch.9 names. Entire LRM subsections have no representation at
all: file I/O (§9.5, 15 tasks), stochastic/probabilistic (§9.9/§9.13, at
least `$random`/`$arandom`/the `$dist_*` family), simulator time functions
beyond `$abstime` (§9.10 — no `$time`/`$realtime`/`$stime`), command-line
input (§9.12), the dynamic simulation probe (§9.16), hierarchical parameter
functions (§9.18), explicit binding detection (§9.19), analog node alias
functions (§9.20), table-based interpolation as a system *function* (§9.21
— distinct from the already-declared `table()` *operator*), and both
driver-access subsections (§9.22/§9.23, also flagged under ch.7 above since
they're `connectmodule`-scoped). Unknown-name lookups do fail loud with
near-match suggestions (`tasks.rs:118-127`), so a call to any of these
missing names is at least a clean, LRM-clause-free E4007 rather than silent
wrong behavior.
