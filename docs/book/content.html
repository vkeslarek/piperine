Chapter 1

Welcome

Goal

By the end of this chapter you have created a project, run an RC filter from the command line, read its results, and made a model tell you what it is doing. You can read a small MSL file from top to bottom.

MSL, the Piperine mixed-signal language, is a language for describing circuits that a simulator runs: analog, digital, and both at once. It looks and reads like Rust, and most of it is Rust. It is similar to Rust and based on it, but it is not Rust: a model describes hardware that exists all the time, not a program that runs once.

This book is for people who want to write models and read other people's models. It teaches the language through complete examples and stands on its own. Each chapter of the language part builds one or two small circuits, explains every new construct the first time it appears, shows how to run the example with the piperine command, lists the mistakes you are most likely to make with the error code you will see, and ends with something to try.

A first look: one resistor

Here is a resistor. It is the smallest useful model, and it already shows the two halves every model has.

/// Ideal resistor.
module Resistor(p: Electrical, n: Electrical) {
    /// Resistance, in ohms.
    r: f64 where r > 0.0;
}

analog for Resistor {
    i(p, n) +> v(p, n) / r;
}

Read it line by line:

  1. module Resistor(p: Electrical, n: Electrical) declares a hardware module with two ports. The type of a port says what flows through it. Electrical is a circuit node: it has a voltage, and currents into it sum to zero.
  2. r: f64 where r > 0.0; is a param. It has a name and a type, and here no default, so whoever places a Resistor must give r. The where clause is a check: a zero or negative resistance is refused before anything is simulated.
  3. analog for Resistor { … } is the behavior. The module says what the thing is (ports, params, structure); a separate block, in the same file, says what it does over time.
  4. i(p, n) +> v(p, n) / r; is Ohm's law. v(p, n) reads the voltage from p to n. i(p, n) +> x adds x to the current that flows from p to n. The arrow +> is called a contribution.

The /// lines are documentation, as in Rust. They stay attached to the module and the param, and tools show them.

The library holds the parts. The resistor you just read is the first of three. This is src/lib.msl:

/// Ideal resistor.
pub module Resistor(p: Electrical, n: Electrical) {
    r: f64 where r > 0.0;
}

analog for Resistor {
    i(p, n) +> v(p, n) / r;
}

/// Ideal capacitor.
pub module Capacitor(p: Electrical, n: Electrical) {
    c: f64 where c > 0.0;
}

analog for Capacitor {
    i(p, n) +> ddt(c * v(p, n));
}

/// A constant voltage from `p` to `n`.
pub module Vsource(p: Electrical, n: Electrical) {
    dc: f64 = 1.0;
}

analog for Vsource {
    v(p, n) +> dc;
}

The bench is the circuit you actually simulate: a module with no ports that places the parts, wires them together and watches them. A bench is written in MSL, like everything else. This is benches/step.msl:

use rc::{Capacitor, Resistor, Vsource};

/// Writes a record when `a` rises through `level`.
module Monitor(a: Electrical) {
    level: f64 = 0.5;
}

digital for Monitor {
    on cross(v(a) - level) {
        emit!("trip", v = v(a));
        require("crossed_upward", v(a) >= level);
    }
}

/// A 1 V source into R and C. `vout` starts at 0 V, so a transient is the step response.
module Step() {
    signal vin: Electrical;
    signal vout: Electrical = 0.0;
    let v1 = Vsource(vin, gnd) { dc: 1.0 };
    let r1 = Resistor(vin, vout) { r: 1k };
    let c1 = Capacitor(vout, gnd) { c: 1n };
    let mon = Monitor(vout);
}

Reading the project

Go back over the three files. Six things are new.

The capacitor. ddt(x) is the time derivative of x. The capacitor's current is the derivative of its charge, c * v(p, n). You write the physics; the simulator differentiates and integrates.

The source. v(p, n) +> dc; contributes to a voltage instead of a current, which makes the branch a voltage source.

SI suffixes. 1k is 103 and 1n is 10−9. A number with an SI suffix is always an f64. A plain 1 is an integer and never turns into an f64 by itself, which is why the defaults read 1.0. (The manifest is TOML, not MSL, so there you write 5e-6.)

The bench is a netlist. Step has no ports and no behavior of its own. signal vin: Electrical; declares a node. let r1 = Resistor(vin, vout) { r: 1k }; places a resistor: the call connects the ports in order, and the braces bind params by name. gnd is the reference node, available everywhere. Every signal and instance gets a path from the top module down, which is what the output shows: Step.vout, Step.mon.

The initial value. signal vout: Electrical = 0.0; makes a transient start with the output at 0 V, a discharged capacitor. An operating point holds nothing, which is why op printed 1 V for the same node.

Two crates. The library under src/ is the package's crate. A bench is a small crate of its own that depends on it, so it imports the parts by the package's name: use rc::{…}, and it sees only what the library marks pub. Stimulus and monitors stay out of the library that other people's designs will use.

Seeing what your model does: emit!

The monitor is seven lines, and it is the most important idea of this chapter:

module Monitor(a: Electrical) { level: f64 = 0.5; }
digital for Monitor {
    on cross(v(a) - level) {
        emit!("trip", v = v(a));
        require("crossed_upward", v(a) >= level);
    }
}

emit! is MSL's print. It is the one output statement of the language, and you will use it in every chapter of this book as your window into a model. Read the block from the outside in:

  • digital for Monitor { … } is the second kind of behavior block. It holds reactions: on event { body } runs the body each time the event fires.
  • cross(e) is an event that fires when the expression e goes from negative to positive. The solver finds the time of the crossing for you; it is not rounded to a time step.
  • "trip" is the name of a stream: an ordered list of records. It must be a string literal.
  • v = v(a) is a field: a name, =, any value. An emit! takes as many as you like. There is no format string. Each field keeps its type.
  • require(name, pass) is a check. It is a library function that itself calls emit!, on the stream checks. A check that passes is not printed unless you ask for it, which is why the run above shows only the trip record.

Each record is printed as one line, the moment it is written:

@6.931075e-7 Step.mon trip v=5.000000e-1

The line has four parts: @ and the time, the path of the instance that wrote the record, the stream name, and the fields. You wrote only the last two; where and when come for free. Two monitors on two nodes never mix their records, because each has its own path.

A design full of checks would bury its own prints under passing checks: a monitor that checks every clock edge writes one record per edge. So the terminal shows a checks record only when it fails, or when its pass is unknown. To see the passing ones too, add --all-checks:

piperine run step --all-checks
@6.931075e-7 Step.mon checks kind="require" name="crossed_upward" pass=true
@6.931075e-7 Step.mon trip v=5.000000e-1

Both records belong to the same instant, and they come in the order the solver hands them over, which here puts the check first. The filter is for your eyes only: a records file (chapter 16) keeps every record, and piperine test counts every check, passing or not.

When a design prints more than you want to read, keep one stream:

piperine run step --stream trip

Three rules make emit! a debugging tool you can trust:

  1. It never changes the simulation. No construct of the language can read a stream. Adding or removing an emit! gives the same waveforms.
  2. A reaction's record is real. A solver often tries a time step, rejects it and tries a shorter one. A record written by a reaction during a step that is later rejected does not exist: what you see in the stream happened.
  3. It goes where behavior goes. emit! is allowed in a reaction and in an analog block, and in a function called from one of them. It is not allowed in a module body.

Chapter 2 compares emit! with Rust's println!, and chapter 6 shows what it does inside analog, where the second rule is different on purpose.

A second bench: a source that steps

The first bench got its step for free, from an initial value. A real stimulus changes during the run. Add a second bench to the project, with a source that switches on at 1 µs:

// benches/delayed.msl
use rc::{Capacitor, Resistor};

/// A voltage step on `p`, referred to ground: 0 V until `t0`, then `v1`.
module StepSource(p: Electrical) {
    v1: f64 = 1.0;
    t0: f64 = 1u where t0 >= 0.0;
    signal fired: Bit = false;
}
digital for StepSource { on at(t0) { fired <- true; } }
analog for StepSource { v(p) +> if fired.high() { v1 } else { 0.0 }; }

module Delayed() {
    signal vin: Electrical;
    signal vout: Electrical;
    let src = StepSource(vin) { v1: 1.0, t0: 1u };
    let r1 = Resistor(vin, vout) { r: 1k };
    let c1 = Capacitor(vout, gnd) { c: 1n };
}
digital for Delayed {
    on cross(v(vout) - (1.0 - 1.0 / E)) {
        emit!("tau", t = now(), vout = v(vout));
    }
}

StepSource is a mixed-signal module, and a tiny one. It has a piece of digital state, signal fired: Bit = false: a one-bit register that starts low. Its reaction, on at(t0) { fired <- true; }, means "when time reaches t0, set fired". The arrow <- is a commit. Its analog block reads that bit: v(p) +> … with one node means "from p to ground", and fired.high() is true when the bit is known and high.

The bench has a reaction of its own this time, on a crossing again, and E is the constant e: the record is written when vout rises through 63.2 % of the step. A bench outside the manifest runs by its file name, with flags in place of the run table's keys:

piperine run benches/delayed.msl --analysis transient --stop 5e-6 --print-step 1e-6
run delayed: transient, top Delayed, backend rust
@2.000428e-6 Delayed tau t=2.000428e-6 vout=6.321206e-1

One time constant after the step: vout is 1 − 1/e to the digit, at 0.4 ns past 2 µs. To keep the run, give it a table in Piperine.toml; every flag has a key of the same name:

[run.delayed]
bench = "benches/delayed.msl"
analysis = "transient"
stop = 5e-6
print_step = 1e-6

Three ways to write

You have now seen two of the three arrows. A model changes the world in exactly three ways, and each has its own operator. Learn these three and you can read any MSL file.

=
definition

y = a & b; drives a digital carrier from an expression, recomputed whenever its inputs change. Written in a module body.

+>
contribution

i(p, n) +> x; adds x to the current (or voltage) of a branch, at every Newton iteration. Written in analog.

<-
commit

q <- d; schedules a new value for a digital carrier at the next microstep. Written in a reaction, on ev { … }.

The third one, the definition, is how you write logic with no state. Here is a digital inverter with a propagation delay. It has no behavior block at all: its one line drives the output from the input, tpd seconds later.

module Inv(in a: Bit, out y: Bit) {
    tpd: f64 = 10p where tpd > 0.0;
    y = !a after tpd;
}

Bit is a logic signal. Digital ports have a direction, in or out; electrical ports have none, because current flows both ways.

Everything else writes nothing. let x = expr; only gives an expression a name. Nets are never "joined" by a statement: you pass the same carrier to two ports, as vout is passed to r1 and c1 above. Parameters have no assignment at all: models read them, and the host sets them.

What you get

One language covers the transistor-level analog model, the RTL-style digital block and the glue between them. A design is fixed at elaboration and then simulated by Piperine's native solver: DC, transient, AC and noise all come from the same source text. Every outcome is a function of the source and of what the host does. There are no races.

A bench, with its sources, its stimulus and its monitors, is written in MSL, as you just did. What stays outside the language is the host: the program that picks the top module, sets parameters, runs analyses and reads the results, streams included. The piperine command is one host. Sweeps over many runs, Monte Carlo and optimization live in a host too, as a Rust program built on the same library.

Status

The specification is complete. The front end that parses MSL and builds the object model (chapter 12) exists and is growing, and it parses and resolves the whole standard library and every complete file of this book. The solver and its device ABI are built (chapters 13 and 14). A first set of analog circuits (resistors, capacitors, sources, a diode with junction limiting) runs on it end to end from source, through an interpreter or as compiled Rust, and is compared with ngspice. Digital and mixed-signal models run from source as compiled Rust: a full-size digitally controlled buck converter starts and regulates with its loop closed (chapter 15). So a file with a digital block, like Monitor above, runs today. The piperine command runs all of it, and every listing of its output in this book is what it prints, checked against the program itself. Parts of the language beyond that are still refused by name with P0001: in analog, noise, idt, delay and math methods such as sin; elsewhere, generic modules, params of an integer type, resolved natures such as Wire and the settle event. When a chapter's example needs one of them, its "Run it" box says so and shows the refusal. This book describes the language as specified.

Chapter 2

If you know Rust

Goal

By the end of this chapter you know which of your Rust habits carry over unchanged, which eleven ideas are new, and you can use emit! the way you use println!, knowing exactly where the two differ.

The rule is short: everything this book does not describe is Rust, edition 2024, with value semantics. Expressions, statements, patterns, match, enums, structs, traits, generics, closures, paths, use and pub all work the way you expect. The language only lists its differences, and so does this chapter.

What carries over

This is valid MSL and valid Rust at the same time. Nothing in it needs explaining:

#[derive(Clone, Copy, PartialEq)]
enum Range { Low, Mid, High }

/// Which third of 0..=255 a code falls in.
fn range_of(code: u8) -> Range {
    match code {
        0..=84 => Range::Low,
        85..=169 => Range::Mid,
        _ => Range::High,
    }
}

fn mean(xs: &[f64]) -> f64 {
    let total: f64 = xs.iter().sum();
    total / xs.len() as f64
}

Functions like these are the "computation" part of a model. What Rust does not have is the hardware around them: things that exist over time and react to each other. That is where the new words come in.

Your first module, read as a Rust programmer

Here is a complete file: a clock, a counter and a top that connects them. It is the "blinky" of this book.

/// A free-running clock of frequency `f`.
module Osc(out clk: Bit = false) {
    f: f64 = 1M where f > 0.0;
}
digital for Osc {
    on clk.changed() { clk <- !clk after 0.5 / f; }
}

/// Counts rising edges, wrapping at 256.
module Counter(in clk: Bit, out count: Bit = 0) {}
digital for Counter {
    on clk.rise() {
        count <- count + 1;
        emit!("edge", t = now(), count = count);
    }
}

module Blinky() {
    signal clk: Bit;
    pub signal count: Bit;
    let osc = Osc(clk) { f: 1M };
    let ctr = Counter(clk, count);
}

Go through it with Rust eyes and note every place where it is not Rust:

  1. module is not mod. A module is a piece of hardware with ports. Rust's mod still exists and is called a namespace module.
  2. A port list is not an argument list. out clk: Bit = false is a wire this module drives, with the value it starts at. in clk: Bit is a wire it only reads. A port exists for the whole simulation; it is not passed once.
  3. A param looks like a struct field. f: f64 = 1M where f > 0.0; has a default and a check. There is no assignment to it anywhere: the placement Osc(clk) { f: 1M } binds it, like a struct literal.
  4. on event { … } is not an if. It is a reaction: the body runs once each time the event fires, forever. clk.changed() fires whenever clk takes a new value; clk.rise() on a rising edge.
  5. <- is not =. count <- count + 1; does not change count now. It schedules the new value, and every read in the same reaction still sees the old one. With after d the new value arrives d seconds later: the oscillator toggles itself every half period, and each toggle is the change that fires the reaction again.
  6. A let in a module body places hardware. let ctr = Counter(clk, count); is an instance named ctr, not a call that returns.

The clock starts at false. That first value is itself a change (from "nothing yet" to low), so the oscillator's reaction fires at time zero and the clock rises for the first time half a period later, at 0.5 µs.

emit! is your println!

The line emit!("edge", t = now(), count = count); writes one record each time the reaction runs. The first three records of a transient look like this, laid out as a table for reading:

stream Blinky.ctr.edge
  instant        fields
  (0.5 µs, 0)    t = 5.0e-7   count = 0
  (1.5 µs, 0)    t = 1.5e-6   count = 1
  (2.5 µs, 0)    t = 2.5e-6   count = 2

Two things to notice. The stream is Blinky.ctr.edge: the name you wrote, under the path of the instance that wrote it, so two counters never mix their records. And the first record says count = 0 although the line above it committed count + 1: a commit takes effect after the reaction, so the record shows the count before the edge. If you want the new value in the record, emit the expression you committed: count = count + 1.

Run it

Save the file as blinky.msl, anywhere. A file with no project around it runs by its name; the flags say which analysis. The top is the one module without ports.

piperine run blinky.msl --analysis transient --stop 3e-6
run blinky: transient, top Blinky, backend rust
@5.000000e-7 Blinky.ctr edge t=5.000000e-7 count=0
@1.500000e-6 Blinky.ctr edge t=1.500000e-6 count=1
@2.500000e-6 Blinky.ctr edge t=2.500000e-6 count=2

These are the three records of the table above, as the command prints them: one line each, live. After them comes a table with the columns Blinky.clk and Blinky.count, the signals of the top. (Today that table is not right yet for a design with no analog node: it holds a single row, at time 0, with the values of the end of the run. The records are right; read them.)

Coming from Rust, this is how the two compare:

Because fields are typed and named, a record is data, not text. A host can plot count against t, compare two runs field by field, or assert on a value, without parsing anything. A message with values in it is simply a record with a text field:

emit!("log", msg = "overrange", vin = v(inp));

The fields are your choice, with three limits: field names within one emit! are distinct, a field of one name has the same type everywhere a stream is written, and the name maybe is taken. The simulator sets maybe = true on a record that was reached under an unknown condition, for example inside an if whose test was unknown. Such a record says "this may have happened", and a host never counts it as a fact.

Two stream names are reserved and global: sim and checks. You do not write to them directly. The standard library does it for you: finish() ends the analysis, and require(name, pass) records a check the host judges. Both are ordinary functions over emit!, and chapter 7 uses them. For a plain message there is log(Severity::Info, "text"), which writes to the instance's log stream.

Good to know

Every emit! in a design is known before the run starts: its stream, its field names and their types. A host lists them and chooses which streams it wants, so you can leave your debug records in a model and decide per run what to look at.

Chapter 3

Values and functions

Goal

By the end of this chapter you can declare your own value types, write the helper functions a model computes with, and explain what an unknown value is, where it comes from and how to catch one with emit!.

A value is data with no time: a number, a flag, an enum, a struct. Everything a model computes with is a value; what it connects to is a carrier (next chapter). This part of the language is Rust, so the chapter moves fast and stops only where MSL differs.

Types

Three differences from Rust matter in practice. Read them in this block of statements:

let a: u8 = 250;
let b = a + 10;            // 4: integers wrap modulo 2^N, in every build, with no panic
let duty: u3 = 5;          // any width: a 3-bit value, 0 to 7
let r = 4.7k;              // an SI suffix makes an f64: 4700.0
let n = 3;                 // a plain literal is an integer
let x = r * n as f64;      // integers and reals never mix by themselves: convert with `as`

First, integers come in any width, because hardware does: a 3-bit duty word is a u3, and a 10-bit ADC code a u10. Second, integer arithmetic wraps the way a register does, in every build; there is no overflow panic to hide a bug in release mode. Third, usize is u64 on every machine, so a result never depends on the computer running it. The prelude gives you the constants Q, K_B, EPS0, PI, E and inf.

Functions

A function is computation without time. It keeps no state, writes no carrier and places no instance. You write it exactly as in Rust:

/// The current of an ideal junction at a voltage `vd`.
pub fn diode_current(vd: f64, is: f64, nvt: f64) -> f64 { is * ((vd / nvt).exp() - 1.0) }

/// A request that is acknowledged in the same cycle.
pub fn handshake(req: Bit, ack: Bit) -> Event { req.rise() && ack }

You never declare where a function may be called. The compiler infers a class from the body: a pure function, like diode_current, works anywhere; one that probes a voltage or reads now() works where the solver is running; one that returns Event, like handshake, works where events go; and one that calls emit! works where emit! does. Inside analog, calls are differentiated automatically, so diode_current needs no hand-written derivative.

Good to know

Anything with state is a module, never a function. fn f(x: f64) -> f64 { ddt(x) } is an error, because ddt remembers the past; write module f(x: f64) -> f64 { ddt(x) }. Chapter 5 shows modules that return values.

Optional parameters

There are no default arguments and no overloading. Instead, trailing parameters of type Option<T> may be left out, or passed by name to skip earlier ones. Passing a plain T wraps it in Some, the one implicit conversion in the language:

/// Scales `x`; the gain is 2.0 unless given, and the result may be clamped.
fn scale(x: f64, k: Option, limit: Option) -> f64 {
    let y = x * k.unwrap_or(2.0);
    match limit { Some(l) => y.clamp(-l, l), None => y }
}
scale(v)                    // k and limit left out
scale(v, 3.0)               // k = Some(3.0)
scale(v, limit: 1.0)        // skips k by naming limit

The library uses this everywhere: idt(x) is an integrator, idt(x, 1.0) one with an initial condition, and idt(x, 1.0, reset: rst) one with a reset too.

Your own types, and Repr

Enums and structs are Rust's. One thing is added: only a type that implements Repr can be carried by a signal. Repr lays a value out as a row of boolean levels, the bits a wire would carry. Primitives have it built in; your own types derive it:

#[derive(Repr, Clone, Copy, PartialEq)]
enum Zone { Under, Ok, Over }

A derived struct puts its fields side by side, first field lowest. A derived enum lays out a tag, then the widest payload. One-hot or Gray encodings are a hand-written impl Repr.

A complete example: a window monitor

Put a type, a function and a module together. This file watches a node and reports, on every clock edge, whether its voltage is under, inside or over a window. The source is a ramp of 1 V/µs, so the node walks through all three zones.

#[derive(Repr, Clone, Copy, PartialEq)]
enum Zone { Under, Ok, Over }

/// Where `x` lies against the window `lo ..= hi`.
fn zone_of(x: f64, lo: f64, hi: f64) -> Zone {
    if x < lo { Zone::Under } else if x > hi { Zone::Over } else { Zone::Ok }
}

/// Samples node `a` on every rising clock edge and reports its zone.
module WindowMonitor(a: Electrical, in clk: Bit, out zone: Bit = Zone::Ok) {
    lo: f64 = 1.0;
    hi: f64 = 2.0 where hi > lo;
}
digital for WindowMonitor {
    on clk.rise() {
        let z = zone_of(v(a), lo, hi);
        zone <- z;
        if z != zone { emit!("zone", t = now(), v = v(a), from = zone, to = z); }
    }
}

/// A voltage that rises from 0 V at `slope` volts per second.
module Ramp(p: Electrical) { slope: f64 = 1M; }
analog for Ramp { v(p) +> slope * now(); }

/// A free-running clock.
module Osc(out clk: Bit = false) { f: f64 = 1M where f > 0.0; }
digital for Osc { on clk.changed() { clk <- !clk after 0.5 / f; } }

module MonitorTop() {
    signal x: Electrical;
    signal clk: Bit;
    pub signal zone: Bit;
    let src = Ramp(x);
    let osc = Osc(clk);
    let mon = WindowMonitor(x, clk, zone);
}

What is new here:

  • out zone: Bit<Zone> = Zone::Ok. A Bit<T> carries any Repr type, so the output of the monitor is the enum itself, not an encoding you have to remember.
  • let z = zone_of(v(a), lo, hi); A local let inside a reaction is an ordinary Rust local. The reaction probes v(a), calls a pure function and gets a value.
  • if z != zone { emit!(…) } prints only when the zone changes. zone on the right still reads the old value (the commit one line up has not applied yet), which is exactly what makes from = zone, to = z correct.
  • A field can be an enum. Any value type is a field; the record keeps Zone::Under as that, not as a number.

The clock rises at 0.5, 1.5 and 2.5 µs, where the ramp is near 0.5, 1.5 and 2.5 V:

stream MonitorTop.mon.zone
  instant        fields
  (0.5 µs, 0)    t = 5.0e-7   v ≈ 0.5   from = Ok      to = Under
  (1.5 µs, 0)    t = 1.5e-6   v ≈ 1.5   from = Under   to = Ok
  (2.5 µs, 0)    t = 2.5e-6   v ≈ 2.5   from = Ok      to = Over

The values of v are "near" on purpose. A reaction that runs on a clock edge reads the analog solution the solver had just before the edge, as a real sampler does. Chapter 8 makes that precise.

Known and unknown

Every level of every value is either known or unknown. This is how MSL models the x of digital logic, and it is not a special kind of wire: the flag travels with the value everywhere, into locals and function arguments too.

Unknown enters a design in only three ways: a carrier that has no value yet, the literal Unknown, or a failed decode. From there it spreads by two rules:

  • Logic works level by level. unknown & false is false and unknown | true is true: a known input that decides the result still decides it.
  • Everything else is all-or-nothing. Arithmetic, comparisons and as give a wholly unknown result if any level of any operand is unknown. a == b is unknown when either side has an unknown level.

An if on an unknown condition does not pick a branch. Both branches run, and their effects are merged: levels on which they agree stay known, the rest become unknown. This is stricter than Verilog, which silently takes the else. When you want that behavior, you say so: if c.known_or(false) { … }.

You read the flag with three methods every Repr value has: x.known() gives an Option (None when any level is unknown), x.known_or(d) gives the value or a default, and x.is_known() a bool.

Catching an unknown with emit!

The classic bug: an input nobody drives. This adder is placed in a top that gives a the constant 3 and takes b from an in port of its own, which nothing drives. (Osc is the clock from the file above.)

/// Registers a + b on every clock edge.
module Adder(in clk: Bit, in a: Bit, in b: Bit, out sum: Bit = 0) {}
digital for Adder {
    on clk.rise() { sum <- a + b; }

    // The debug reaction: fires when `sum` changes and is no longer known.
    on sum.changed() && !sum.is_known() {
        emit!("lost", t = now(), a = a, b = b);
    }
}

module AdderTop(in b: Bit) {
    signal clk: Bit;
    pub signal sum: Bit;
    let osc = Osc(clk);
    let add = Adder(clk, 3, b, sum);
}

An in port may be connected to an expression, here the literal 3. A top-level in port that nothing drives stays unknown. On the first clock edge the adder computes 3 + unknown, which is unknown, and commits it: sum goes from 0 to unknown. Going from known to unknown is a change, so the second reaction fires. Its guard, !sum.is_known(), is an ordinary bool. The record tells you which input to blame, because a field keeps its known flag:

stream AdderTop.add.lost
  instant        fields
  (0.5 µs, 1)    t = 5.0e-7   a = 3   b = unknown

The instant is (0.5 µs, 1), not (0.5 µs, 0): the clock edge is microstep 0, and the commit to sum applies one microstep later. Only one record is written, because unknown to unknown is not a change.

Add the two modules to monitor.msl. The file now has two candidates for the top, so name the one you want. Its in port is left undriven, which is the bug under study:

A second flavor of the same tool: a record reached under an unknown condition is written with maybe = true. If the adder also had if a > b { emit!("bigger", a = a); }, that record would appear here marked maybe: the model cannot tell whether a > b, and it says so instead of guessing.

Analog code has no unknowns

The analog solver computes with real numbers only, so an analog block must say what an unknown means electrically. It reads a digital carrier through known(), known_or(d) or, for a Bit, high() (known and true):

module SampleHold(vin: Electrical, vout: Electrical, in clk: Bit) { signal held: Bit = 0.0; }
digital for SampleHold { on clk.rise() { held <- v(vin); } }
analog for SampleHold { v(vout) +> held.known_or(0.0); }

Writing v(vout) +> held; instead is error E0150, and the diagnostic names the carrier. The model says what an unknown means electrically; the language does not guess. This holds even for a carrier that, like held, can never be unknown: the rule is about what you wrote, not about what the compiler can prove.

Foreign functions

A function written in C is declared with extern "C" and no body. To use it inside analog, name its derivatives, one per f64 argument, because the compiler cannot look inside:

#[derivative(erfcx_dx)] extern "C" fn erfcx(x: f64) -> f64;
extern "C" fn erfcx_dx(x: f64) -> f64;

Chapter 4

Natures and carriers

Goal

By the end of this chapter you can pick the right kind of wire for a job, declare signals and ports of every kind, and build a shared open-drain line that several modules drive, with a monitor that prints every change of it.

A carrier is something that exists over time: a wire, a node, a register. You have used three already: the node vout, the clock clk and the register count. Every carrier has a nature, and the nature answers two questions: what does it hold, and what happens when several modules drive it.

Two questions, four answers

Think about real wires. A logic net driven by one gate holds one value and has one owner. An open-drain bus has many drivers and a rule for combining them. A circuit node has no "driver" at all: every element connected to it pushes or pulls current, and Kirchhoff's law settles the voltage. A block-diagram signal, such as the output of an ideal amplifier, is a voltage with one source and no current. MSL has exactly these four kinds:

How a nature is declared

Natures are ordinary declarations. These are the ones the standard library gives you:

nature Bit { value: T }                              // prelude; Bit is Bit
nature Wire { value: Logic, resolve: Logic::wired }                  // stdlib: strengths, high impedance
nature Electrical {
    potential: Voltage { access: v, units: "V", abstol: 1u },
    flow:      Current { access: i, units: "A", abstol: 1p },
}
nature Thermal {
    potential: Temperature { access: temp, units: "K", abstol: 1m },
    flow:      Power       { access: pwr,  units: "W", abstol: 1n },
}
nature VSignal { potential: Voltage { access: v, units: "V", abstol: 1u } }   // signal-flow

The body tells you the family. A discrete nature declares value: the type it holds. Add resolve, a function from all the drives to one value, and it accepts many drivers. A continuous nature declares potential, and usually flow.

The access names become the probes you already used: v(a, b) reads a voltage and i(a, b) a current on Electrical; temp and pwr do the same on Thermal. units is a label for people and is never checked. abstol is the solver's tolerance for that quantity: a voltage is "converged" to about a microvolt, a current to a picoamp. There is no inheritance between natures; a high-voltage variant of Electrical is a second nature.

Signals

Inside a module, signal declares a carrier. An initial value is optional, and what it means depends on the family:

signal en:    Bit;                       // starts unknown
signal count: Bit = 0;               // starts at 0
signal level: Bit = 0.0;            // a real number that changes in steps
signal lines: [Bit; 8];                  // eight carriers, each with its own events
signal bus:   Bit = logic("10xx");   // level by level; x is unknown
signal sda:   Wire;                      // resolved: any number of drivers
signal mid:   Electrical;                // an internal node
signal vout:  Electrical = 0.0;          // where Newton starts; held there as a transient begins

A discrete signal with no initial value starts unknown and stays so until something commits to it. That is the honest model of a register at power-up, and chapter 3 showed how to catch it. On a node, = 0.0 is where the solver begins its search for the operating point, and a transient analysis starts from that value.

An array of carriers costs what you write into it: storage for an element exists from its first commit, so [Bit<u8>; 1 << 32] is fine as a memory.

Ports

A port is a carrier that comes from outside. The port list decides what kind each port is, from its type:

A complete example: one line, many drivers

Two sensors share one active-low alarm line. Each may pull it low; a pull-up keeps it high when nobody does. With a Bit this cannot be built: a Bit has one driver, and the second one is an error. The line is a Wire.

/// Pulls the line low while `req` is high, and lets go of it otherwise.
module OpenDrain(in req: Bit, line: Wire) {
    line = if req { Logic::strong(false) } else { Logic::Z };
}

/// Reports every change of a line.
module LineWatch(line: Wire) {}
digital for LineWatch {
    on line.changed() {
        emit!("line", t = now(), level = line.v, strength = line.s);
    }
}

/// The bench: the line, its drivers, and the two sensors as stimulus.
module Alarm() {
    signal door: Bit = false;
    signal window: Bit = false;
    signal alarm_n: Wire;
    let pu = Pullup(alarm_n);
    let d0 = OpenDrain(door, alarm_n);
    let d1 = OpenDrain(window, alarm_n);
    let watch = LineWatch(alarm_n);
}
digital for Alarm {
    on at(1u) { door <- true; }
    on at(2u) { window <- true; }
    on at(3u) { door <- false; window <- false; }
}

Line by line:

  • line: Wire has no direction. Any module that sees a Wire may drive it, and nobody counts drivers.
  • line = if req { … } else { … }; is a definition, the = arrow of chapter 1: it is recomputed whenever req changes. What it defines is this module's drive of the line, not the line itself.
  • Logic is the value a Wire holds: a level v and a strength s. Logic::strong(false) is a hard low; Logic::Z is "not driving". Pullup, from the library, drives a high of the weaker strength Pull: Logic::pull(true).
  • The line's value is its nature's resolve applied to all the drives: the strongest wins, and equal strengths that disagree give unknown.
  • line.v and line.s read the two fields of the resolved value, like a struct.

The last block is the stimulus, and it is ordinary MSL: the bench owns the two sensor signals, starts them low, and three timed reactions raise door at 1 µs, raise window at 2 µs, and drop both at 3 µs. The monitor writes:

stream Alarm.watch.line
  instant      fields
  (0, 0)       t = 0        level = true    strength = Pull
  (1 µs, 1)    t = 1.0e-6   level = false   strength = Strong
  (3 µs, 1)    t = 3.0e-6   level = true    strength = Pull

Three records, not four. At 2 µs the second driver joins, but the resolved value is still a strong low, so the line did not change and changed() did not fire. That is the question a debug print should answer: not "what did I write" but "what does the wire hold".

The first record is at time zero: the initial values of a design are themselves a change, from nothing to something, so reactions on changed() run once at the start.

Two continuous natures in one module

Continuous natures compose the same way. A resistor that heats itself has two electrical ports and one thermal port, and its behavior reads one world and writes the other:

/// A resistor whose value follows the temperature rise on `t`.
module HotResistor(p: Electrical, n: Electrical, t: Thermal) {
    r0: f64 where r0 > 0.0;
    /// Temperature coefficient, per kelvin.
    tc: f64 = 4m;
}
analog for HotResistor {
    let r = r0 * (1.0 + tc * temp(t));
    i(p, n) +> v(p, n) / r;
    pwr(t) +> -v(p, n) * v(p, n) / r;       // the dissipated power flows into `t`
}

/// A thermal resistance from `t` to ambient.
module ThermalR(t: Thermal) { rth: f64 where rth > 0.0; }
analog for ThermalR { pwr(t) +> temp(t) / rth; }

temp(t) is the potential of the thermal node, pwr(t) its flow to the reference. A contribution pwr(t) +> x takes x out of the node, so power into the node is negative. Connect HotResistor and ThermalR to the same thermal node and the solver finds the temperature at which the power in equals the power out.

Bundles

A struct whose fields are all carriers is a bundle: a cable. Directions are written once, from the producer's side, and flip gives the consumer's view. Here is a valid/ready stream and a register slice that sits in the middle of one. It reads rx as a consumer and drives tx as a producer:

struct Stream { out valid: Bit, in ready: Bit, out data: Bit }
impl Stream {
    /// A transfer happens on this clock edge.
    pub fn beat(self, clk: Bit) -> Event { clk.rise() && self.valid && self.ready }
}

module Slice(in clk: Bit, rx: flip Stream, tx: Stream) {
    signal full: Bit = false;
    signal buf: Bit;
    tx.data = buf;
    tx.valid = full;
    rx.ready = !full || tx.ready;
}
digital for Slice {
    on rx.beat(clk) { buf <- rx.data; full <- true; }
    on clk.rise() && !(rx.valid && rx.ready) && tx.ready { full <- false; }
}

For tx, a plain Stream, the slice drives valid and data and reads ready. For rx, flipped, it is the other way around, which is why the body may define rx.ready. A bundle can carry methods too: rx.beat(clk) is an event you can react to.

Analog and digital never touch directly

A Bit is never connected to an Electrical node, and no converter is ever inserted for you. Between modules you place one explicitly: D2A, A2D or Bidir from the standard library. Inside one module, behavior crosses freely: analog reads digital carriers, and reactions probe voltages, as Step and WindowMonitor already did. Chapter 8 is about this.

Chapter 5

Modules and hierarchy

Goal

By the end of this chapter you can build a design out of smaller modules: place instances, bind params, generate a row of stages with a loop, look inside a child from its parent, and write a module that returns a value, such as a filter you can call inside an expression.

A module is ports, params and a netlist of signals and instances, all fixed at elaboration: the moment, before any simulation, when the design is unfolded into its final list of instances. Its behavior over time lives in separate analog for and digital for blocks, in the same file.

The body is a netlist

A module body is not a sequence of statements. It is a list of things that exist. Items can come in any order, and every name is visible in the whole body and in the module's blocks:

ItemExampleWhat it is

Params. A param without a default is required. One of type Option<T> may be left out. A where clause is a check over this param and earlier ones, for example n: f64 = 1.0 where (0.1..=10.0).contains(&n);. A param that decides the shape of the design (a loop bound of generation, an array length, a const generic argument) is structural: it is fixed at elaboration, and a host cannot change it during a run.

A body let is not a variable. let half = r / 2.0; stores nothing. It is a name for the expression, and the expression is evaluated wherever the name is read. That is why there is no let mut in a body: there is nothing to mutate.

A complete example: an RC ladder

Build a three-section RC ladder out of the Resistor and Capacitor of chapter 1. The file has three levels of hierarchy: a section, a ladder of N sections, and a top with a source.

module Resistor(p: Electrical, n: Electrical) { r: f64 where r > 0.0; }
analog for Resistor { i(p, n) +> v(p, n) / r; }

module Capacitor(p: Electrical, n: Electrical) { c: f64 where c > 0.0; }
analog for Capacitor { i(p, n) +> ddt(c * v(p, n)); }

/// A constant voltage on `p`, referred to ground.
module Vdc(p: Electrical) { dc: f64 = 1.0; }
analog for Vdc { v(p) +> dc; }

/// One section: a series R from `a` to `b`, and a C from `b` to ground.
module RcSection(a: Electrical, b: Electrical) {
    r: f64 = 1k where r > 0.0;
    c: f64 = 1n where c > 0.0;
    let r1 = Resistor(a, b) { r: r };
    let c1 = Capacitor(b, gnd) { c: c };
}

/// `N` sections in a row, from `a` to `b`.
module Ladder(a: Electrical, b: Electrical) where N >= 1 {
    r: f64 = 1k;
    c: f64 = 1n;
    /// tap[0] is the input, tap[N] the output.
    pub signal tap: [Electrical; N + 1];
    let head = Short(a, tap[0]);
    let tail = Short(tap[N], b);
    for k in 0..N {
        pub let sec = RcSection(tap[k], tap[k + 1]) { r, c };
    }
}

module LadderTop() {
    signal vin: Electrical;
    pub signal vout: Electrical;
    let src = Vdc(vin) { dc: 1.0 };
    pub let lad = Ladder::<3>(vin, vout) { r: 1k, c: 1n };
}

Take the new constructs one at a time.

  1. Placing an instance. let r1 = Resistor(a, b) { r: r }; has three parts: a name (r1), the connections in port order (a, b), and a param block that binds by name. In { r: r } the left r is the resistor's param and the right one is the section's. When both names are equal you may write just { r, c }, as the ladder does.
  2. A const generic. Ladder<const N: usize> takes the number of sections as a generic argument, and where N >= 1 refuses an empty ladder. The top picks it with Ladder::<3>(…).
  3. An array of nodes. signal tap: [Electrical; N + 1]; declares four nodes here. tap[k] names one of them.
  4. Generation. for k in 0..N { … } in a body is not a loop that runs during simulation. It is unrolled at elaboration: three sections are placed, each an instance of its own, named sec[0], sec[1] and sec[2].
  5. Short. A library module that makes two nodes one. It joins the ports to the two ends of the array.
  6. pub. A parent can reach into a child only through what the child marks pub. The ladder publishes its taps and its sections; it keeps head and tail to itself.

Every instance and carrier of the elaborated design has a path: the name of the top module, then the names of the instances from the top down, joined by dots. The capacitor of the middle section is LadderTop.lad.sec[1].c1, and its param is LadderTop.lad.sec[1].c1.c. A host uses these paths to probe a node or set a param, and a record's stream name starts with the path of the instance that wrote it.

Looking inside from the parent

Because the taps are pub, the top can watch them. Swap the DC source for the Step of chapter 1 and add a block that reports when each tap passes half of the step:

digital for LadderTop {
    for k in 1..4 {
        on cross(v(lad.tap[k]) - 0.5) { emit!("half", stage = k, t = now()); }
    }
}

Generation works in a digital block too: this is three reactions, one per tap. lad.tap[k] goes through the instance lad to its public array. The loop index is an ordinary value, so it can be a field. The stream gets one record per stage, in order, because the edge reaches the taps one after another:

stream LadderTop.half
  fields
  stage = 1   t = …
  stage = 2   t = …
  stage = 3   t = …

The times are left for you; the exercise at the end of the chapter gives an estimate to check them against.

Modules that return a value

So far a module was something you wire up. A module may also take value inputs and end its body with a result, declared with -> T. Then you call it inside an expression, and every call is an instance with its own state. This is the tool for "a function with memory".

Here is a first-order low-pass you can apply to any expression:

/// `x` smoothed with time constant `tau`. A module, because it remembers.
module lowpass(x: f64, tau: f64) -> f64 {
    let y = idt((x - y) / tau);
    y
}

/// A buffer whose output follows its input through a 1 µs low-pass.
module SlowBuffer(a: Electrical, b: Electrical) {}
analog for SlowBuffer { v(b) +> lowpass(v(a), 1u); }

Three things happen in lowpass:

  • x: f64 and tau: f64 are value inputs. They are ports whose type is a plain value. At each instance they stand for the expressions the caller wrote, here v(a) and 1u.
  • idt(e) is the time integral of e, itself a library module that returns a value.
  • y reads itself. let y = idt((x - y) / tau); is the differential equation dy/dt = (x − y) / tau, written directly. An instance may read its own result when, as here, a state stands between the read and the write.

The last line, y with no semicolon, is the result. Every operator with memory in the language is built this way: ddt, idt, delay, cross, transition. The standard integrator itself is written in MSL:

pub module idt(x: f64, ic: Option, reset: Option) -> f64 {
    signal y: S;
    potential(y)                             // the result
}

analog for idt {
    let hold = reset.unwrap_or(false) || (ic.is_some() && analysis(Static));
    if hold { potential(y) +> ic.unwrap_or(0.0); } else { flow(y) +> ddt(potential(y)) - x; }
}

A bigger example of the same idea: a PI controller with output limits. Its integral reads its own result to stop winding up when the output saturates.

fn windup(u: f64, lo: f64, hi: f64) -> f64 { u.clamp(lo, hi) - u }

/// PI with output limits and back-calculation anti-windup: the integral reads its own result.
module PiAw(e: VSignal, y: VSignal) {
    kp: f64 = 0.5; ki: f64 = 2k; kt: f64 = 10k;
    lo: f64 = 0.0; hi: f64 = 1.0 where hi > lo;
    let xi = idt(ki * v(e) + kt * windup(kp * v(e) + xi, lo, hi));
}
analog for PiAw { v(y) +> (kp * v(e) + xi).clamp(lo, hi); }

Good to know

Every placement is one instance. let acc = idt(v(a)); names one integrator, and every read of acc is that same integrator. Two calls with equal arguments are two integrators. When you need one state read in two places, name it with a let.

Structure without behavior

Many useful modules have no behavior block at all. Here is a switched-capacitor integrator that is only a netlist of smaller parts. Chapter 6 walks through what the solver does with it.

module RSwitch(a: Electrical, b: Electrical, in ctl: Bit) { ron: f64 = 100.0; roff: f64 = 1G; }
analog for RSwitch { i(a, b) +> v(a, b) / if ctl.high() { ron } else { roff }; }

module OpAmpIdeal(inp: Electrical, inn: Electrical, vout: Electrical) { a0: f64 = 1e5; }
analog for OpAmpIdeal { v(vout) +> a0 * v(inp, inn); }

/// Non-overlapping two-phase clock: pure structure.
module TwoPhase(in clk: Bit, out phi1: Bit = false, out phi2: Bit = false) {
    gap: f64 = 50p;
    phi1 = clk after if clk { gap } else { 0.0 };      // rises gap after clk, falls with it
    phi2 = !clk after if clk { 0.0 } else { gap };     // the mirror
}

/// Stray-insensitive SC integrator: structure only.
module ScIntegrator(vin: Electrical, vout: Electrical, in clk: Bit) {
    cs: f64 = 1p; cf: f64 = 4p;
    signal phi1: Bit;
    signal phi2: Bit;
    signal x: Electrical;
    signal y: Electrical;
    signal vg: Electrical;
    let ck = TwoPhase(clk, phi1, phi2);
    let s1 = RSwitch(vin, x, phi1);
    let s2 = RSwitch(x, gnd, phi2);
    let s3 = RSwitch(y, gnd, phi1);
    let s4 = RSwitch(y, vg, phi2);
    let csmp = Capacitor(x, y) { c: cs };
    let cfb = Capacitor(vg, vout) { c: cf };
    let amp = OpAmpIdeal(gnd, vg, vout);
}

Notice ron: f64 = 100.0, not 100: an integer literal never becomes an f64, while an SI literal like 1G always is one.

A parent may also add its own behavior on a child's public node. A SAR ADC hangs a parasitic capacitor on the output node of its DAC this way: analog for SarAdc { i(dac.core) +> ddt(cpar * v(dac.core)); }.

Templates: modules as values

A module with its params bound is a value, called a template: Name { params }. You can pass it as a param and place it later. That makes cells swappable. A memory array does not need to know which cell it is made of:

/// What a memory cell connects to: a word line and a bit line.
struct Cell { in wl: Bit, bl: Electrical }

/// One-transistor one-capacitor DRAM cell.
module Dram1T1C(c: Cell) {

    ron: f64 = 5k;
    rleak: f64 = 1T;
    pub signal sn: Electrical = 0.0;     // storage node
}

module MemoryBank(in wl: [Bit; ROWS], bl: [Electrical; COLS]) {
    cell: C;

}

Chapter 6

Analog behavior

Goal

By the end of this chapter you can write a nonlinear device, build a diode clipper around it with a sine source, print its waveform and its clipping instants, and use a trace inside analog to see what Newton's method is doing when a circuit will not converge.

An analog block is the equations of a module. To find the voltages of a circuit, the solver guesses them, evaluates every analog block, corrects the guess and repeats: that is Newton's method, and each round is an iteration. So keep one picture in mind for the whole chapter: an analog block is straight-line code that runs at every Newton iteration and remembers nothing between iterations. The past comes only from instances such as ddt and idt, and from digital carriers.

Contributions and probes

A branch is a pair of nodes. A probe reads it: v(a, b) is the voltage from a to b, and i(a, b) the current this module puts through that branch. A contribution writes it, in one of two ways:

  • i(a, b) +> x; adds x to the branch's current. The branch behaves as a current source of value x, and x usually depends on v(a, b): that is a resistor, a diode, a capacitor.
  • v(a, b) +> x; adds x to the branch's voltage. The branch becomes a voltage source, and the solver finds the current it needs.

Contributions add up, which is why the arrow has a plus in it: two lines that contribute to the same branch are two elements in parallel. Leave out the second node and it is gnd.

module Capacitor(p: Electrical, n: Electrical) { c: f64 where c > 0.0; }
analog for Capacitor { i(p, n) +> ddt(c * v(p, n)); }      // i = dq/dt

module Inductor(p: Electrical, n: Electrical) { l: f64 where l > 0.0; }
analog for Inductor  { v(p, n) +> ddt(l * i(p, n)); }      // v = dφ/dt

The two are mirror images. The capacitor contributes a current computed from its voltage. The inductor contributes a voltage computed from its own current: once a branch has a voltage contribution, i(p, n) reads the current the solver found for it.

You never write a derivative of your equations. Everything is differentiated for you, through function calls, value inputs and results, so there is no Jacobian to get wrong.

A complete example: a diode clipper

A 2 V sine drives a resistor into two diodes back to back. The output follows the input while it is small and is clipped near ±0.65 V.

module Resistor(p: Electrical, n: Electrical) { r: f64 where r > 0.0; }
analog for Resistor { i(p, n) +> v(p, n) / r; }

/// A sine voltage source of amplitude `amp` and frequency `f`.
module Vsin(p: Electrical, n: Electrical) {
    amp: f64 = 1.0;
    f: f64 = 1k where f > 0.0;
}
analog for Vsin {
    v(p, n) +> amp * (2.0 * PI * f * now()).sin();
    bound_step(0.02 / f);                    // never fewer than 50 points per period
}

/// Junction diode: i = is · (exp(v / (n · vt)) − 1).
module Diode(a: Electrical, k: Electrical) {
    is: f64 = 1e-14 where is > 0.0;
    n: f64 = 1.0 where n > 0.0;
}
analog for Diode {
    let nvt = n * vt();
    i(a, k) +> is * (limexp(v(a, k) / nvt) - 1.0);
}

module Clipper() {
    signal vin: Electrical;
    pub signal vout: Electrical;
    let src = Vsin(vin, gnd) { amp: 2.0, f: 1k };
    let r1 = Resistor(vin, vout) { r: 1k };
    let d1 = Diode(vout, gnd);
    let d2 = Diode(gnd, vout);
}

The new pieces, in order:

  1. now() is the simulation time, so the source is a plain function of time. In an operating-point solve now() is 0 and the source sits at 0 V.
  2. bound_step(dt); is a statement only analog has. It caps the next time step. The solver picks steps from the circuit's own dynamics, and a smooth source into a stiff clipper could be stepped over; this line guarantees the sine is sampled finely.
  3. let nvt = n * vt(); A let inside analog is a local of this iteration. vt() is the thermal voltage kT/q at the simulation temperature, about 25.9 mV at the default 300.15 K.
  4. limexp(x) equals x.exp() once the solver has converged, but while it iterates it lets the argument move only a little per iteration. An exponential explodes when Newton overshoots; limexp is the standard cure and costs you nothing in accuracy.
  5. Diode(vout, gnd) binds no params, so both diodes take the defaults.

Printing the waveform: on settle

To see the clipper work you want vin and vout over time. The event for that is settle. It fires once per time point, the times at which the solver has an accepted solution, after everything else at that time has finished. A reaction on settle reads the solution of that time point:

digital for Clipper {
    on settle {
        emit!("wave", t = now(), vin = v(vin), vout = v(vout));
    }
    on cross(v(vout) - 0.6) {
        emit!("clip", t = now(), vin = v(vin));
    }
}

The wave stream is the table you would plot: one record per accepted time point, none for a step the solver tried and threw away. The clip stream answers a sharper question, "when does the clipping start, and how high is the input then?". The solver locates the crossing in time, so the answer does not depend on where the time points happened to fall:

stream Clipper.clip
  instant           fields
  (≈ 59 µs, 1)      t ≈ 5.9e-5    vin ≈ 0.72
  (≈ 1.059 ms, 1)   t ≈ 1.059e-3  vin ≈ 0.72
  …                 once per period

At 0.6 V the diode carries about 0.12 mA, which drops 0.12 V over the resistor, so the input is at 0.72 V: the record confirms the hand calculation.

Looking inside Newton: emit! in analog

emit! is also allowed directly in an analog block, and there it behaves differently, on purpose. Add one line to the diode:

analog for Diode {
    let nvt = n * vt();
    let id = is * (limexp(v(a, k) / nvt) - 1.0);
    i(a, k) +> id;
    emit!("newton", vd = v(a, k), id = id);
}

This emit! runs when the code around it runs, and analog runs at every evaluation: every Newton iteration of every step, including iterations and whole steps that the solver later rejects. Each record also carries the iteration number. The stream is a trace of the path Newton took:

stream Clipper.d1.newton               one record per evaluation
  time    iteration   fields

The piperine command prints the records of reactions; a trace from analog is not among the lines it shows. Where a trace is available, it is exactly what you need when a circuit does not converge: you see the voltage a device was asked to evaluate at each iteration, and whether it is settling, oscillating or running away. It is also why a trace is never used for a result. Keep the two kinds of output apart:

Switching a branch

An if in analog can choose between contributions. This ideal switch is a short when closed and an open circuit when open:

module Switch(a: Electrical, b: Electrical, in ctl: Bit) {}
analog for Switch {
    if ctl.high() { v(a, b) +> 0.0; } else { i(a, b) +> 0.0; }
}

It shows the one firm restriction of the chapter. A branch may change between being a voltage branch and a current branch, but only on something that is constant during a solve: params, digital carriers, now(), analysis(Static). A choice of kind that depends on a probe is an error (E0414), because the solver would have to change the equations while it is solving them. An if on a probe can still choose between expressions: i(a, b) +> v(a, b) * if v(a, b) > 0.0 { g1 } else { g2 }; is fine.

A few more shapes

Two patterns you will meet in other people's models. The first writes an equation rather than an element: a node of a helper nature holds a free unknown, and its flow is the residual the solver drives to zero. The second couples two branches inside one module.

/// An equation is a row: a nature whose "flow" is the residual gives it the right tolerance.
nature Servo {
    potential: Voltage { access: v,   abstol: 1u },
    flow:      Voltage { access: err, abstol: 1u },
}

/// Ideal op-amp (nullor): drives vout so that v(inp, inn) == 0.
module Nullor(inp: Electrical, inn: Electrical, vout: Electrical) { signal x: Servo; }
analog for Nullor {
    err(x) +> v(inp, inn);  // the row of x carries the equation, tested against 1 µV
    v(vout) +> v(x);        // v(x) is the free unknown
}

/// Two coupled inductors: coupling is inside one module, which writes only its own branches.
module Coupled(p1: Electrical, n1: Electrical, p2: Electrical, n2: Electrical) {
    l1: f64; l2: f64; k: f64 where k.abs() <= 1.0;
    let mu = k * (l1 * l2).sqrt();
}
analog for Coupled {
    v(p1, n1) +> ddt(l1 * i(p1, n1) + mu * i(p2, n2));
    v(p2, n2) +> ddt(l2 * i(p2, n2) + mu * i(p1, n1));
}

Walkthrough: the switched-capacitor integrator

Go back to ScIntegrator in chapter 5. It has no analog block of its own: all branches belong to its children. Here is what the solver sees.

  1. Operating point. Both clock phases start low, so all four switches are at roff and the capacitors carry no current. y and vg reach ground through s3 and s4; x sits at v(vin)/2 between s1 and s2. No node floats. That is what a finite roff buys.
  2. Sampling, phi1 high. x follows vin and y is grounded, so cs charges to v(vin), with a time constant of ron · cs = 0.1 ns per switch.
  3. Transfer, phi2 high. x is grounded and y joins the virtual ground vg. The charge cs · v(vin) moves onto cf.
  4. Per period. Charge is conserved at vg, so vout[n] = vout[n−1] + (cs/cf) · vin[n]: a non-inverting integrator with gain 0.25.
  5. Time points. Each phase edge changes a switch conductance that analog reads, so the solver lands exactly on all four edges per period. Capacitor charges stay continuous; only the currents step.
  6. DC and AC. DC solves the all-switches-off circuit above, not the sampled system. The AC sweep linearizes with both phases low. The sampled transfer function needs a periodic analysis.

Chapter 7

Digital behavior

Goal

By the end of this chapter you can write clocked logic and predict it edge by edge: a counter, a debounced button and a PWM generator, each with a debug stream that shows its state on every clock edge. You will also know the one rule that makes digital MSL free of races.

A digital block holds reactions. A reaction on ev { body } runs its body once, to completion, each time the event ev fires. Inside it, q <- x; is a commit: it writes this module's drive of q, and the write takes effect a moment later, never during the reaction.

The one rule: reads see the past

Start with a counter that also raises a flag when it is about to wrap. The first line of the reaction is a debug print of the state.

module Counter(in clk: Bit, out count: Bit = 0, out full: Bit = false) {}
digital for Counter {
    on clk.rise() {
        emit!("state", t = now(), count = count, full = full);
        count <- count + 1;
        full  <- count == 254;
    }
}

Why 254 and not 255? Because every read in a reaction sees the values from before the edge, exactly like the D inputs of real flip-flops. On the edge where count reads 254, the first commit schedules 255 and the second schedules full = true; both land together. So full is high exactly while count is 255. The stream shows it:

stream Count.ctr.state               (a 1 MHz clock: edges at 0.5, 1.5, 2.5 µs, …)
  instant         fields
  (0.5 µs, 0)     count = 0     full = false
  (1.5 µs, 0)     count = 1     full = false
  …
  (254.5 µs, 0)   count = 254   full = false     this edge commits 255 and full = true
  (255.5 µs, 0)   count = 255   full = true      this edge commits 0 and full = false
  (256.5 µs, 0)   count = 0     full = false

Each record is the state the reaction found. Put the emit! first, last or in the middle: it prints the same thing, because nothing changes while a reaction runs. This is the habit to build: one emit!("state", …) at the top of a clocked reaction gives you the whole history of the block, one row per edge.

The counter needs a clock. Put it in a file count.msl with the Osc of chapter 2 and a three-line bench:

    signal count: Bit;
    signal full: Bit;

The rules of a microstep

Time in digital MSL advances in microsteps: at one time t, the instants (t, 0), (t, 1), (t, 2), … follow each other until nothing is left to do. A commit made at microstep n applies at microstep n + 1. The second number in every record's instant is this counter. Five rules govern it:

  • Reads see the past. Every read sees the values at the start of the microstep. All the commits of a microstep apply together. That is why statement order inside a reaction rarely matters.
  • The last write wins. When two commits hit the same level in the same microstep, source order decides. All writers of one drive are in one module, so you can see the order in one file.
  • Modules never race. A one-driver carrier has one writer, and a resolved one combines its drives in a fixed order. No result depends on which module the simulator happened to run first.
  • Delays are transport. q <- x after d; applies d seconds later. A new commit from the same statement removes that statement's pending commits due at or after it. p <- true; p <- false after w; is a pulse of width w, in either order.
  • A reaction never waits. There is no wait, no blocking write and no #0. A sequence over time is visible state, such as a counter.

Definitions and commits

A module drives a carrier in one of two ways, never both: with one = definition in the body, or with commits from its reactions. Use a definition for combinational logic and delays, and commits for state. A definition is recomputed in the same microstep its inputs change, so it never lags. A set-reset latch needs no reaction at all:

/// Cross-coupled NOR gates with gate delay: pure structure.
module SrLatch(in s: Bit, in r: Bit, out q: Bit = false, out qn: Bit = true) {
    tpd: f64 = 10p where tpd > 0.0;
    q  = !(r | qn) after tpd;
    qn = !(s | q)  after tpd;
}

Without the after, the two definitions would form a loop with no delay in it, which is an elaboration error (E0339).

/// Three-state phase detector: two events in one reaction, each tested as a bool.
module Pfd3(in fref: Bit, in fvco: Bit, out up: Bit, out dn: Bit) {
    signal state: Bit = 0;
    up = state == 1;
    dn = state == -1;
}
digital for Pfd3 {
    on fref.rise() || fvco.rise() {
        let mut s = state;
        if fref.rise() && s < 1 { s += 1; }    // which one fired?
        if fvco.rise() && s > -1 { s -= 1; }   // both at once: up first, then down
        state <- s;
    }
}

Inside a reaction, let mut is back: a local is an ordinary Rust variable that lives for one run of the body. Only carriers follow the "reads see the past" rule.

A complete example: a debounced button

A mechanical button bounces for a few milliseconds. The classic fix samples it with a slow clock and accepts a new level only after it has been seen on several consecutive samples.

/// A free-running clock.
module Osc(out clk: Bit = false) { f: f64 = 1M where f > 0.0; }
digital for Osc { on clk.changed() { clk <- !clk after 0.5 / f; } }

/// `clean` follows `raw` once `raw` has differed from it on `n` consecutive clock edges.
module Debounce(in clk: Bit, in raw: Bit, out clean: Bit = false) {
    n: u8 = 4 where n >= 1;
    /// Consecutive samples that differ from `clean`.
    signal run: Bit = 0;
}
digital for Debounce {
    on clk.rise() {
        emit!("state", t = now(), raw = raw, run = run, clean = clean);
        let level = raw.known_or(clean);        // an unknown input counts as "no change"
        if level == clean {
            run <- 0;
        } else if run + 1 >= n {
            clean <- level;
            run <- 0;
            emit!("flip", t = now(), to = level);
        } else {
            run <- run + 1;
        }
    }
}

/// The bench: a clock, the debouncer, and a button that bounces.
module Press() {
    signal clk: Bit;
    signal button: Bit = false;
    pub signal pressed: Bit;
    let osc = Osc(clk) { f: 1k };
    let db = Debounce(clk, button, pressed) { n: 4 };
}
digital for Press {
    on at(2.0m) { button <- true; }
    on at(2.2m) { button <- false; }
    on at(2.4m) { button <- true; }
}

Read the reaction as a hardware designer would read RTL:

  • signal run: Bit<u8> = 0; is the state register: how many samples in a row disagreed with the output.
  • raw.known_or(clean) decides what an undriven button means. Here it means "same as now", so an unknown input can never flip the output.
  • The three arms are: agreement resets the run; the n-th disagreement flips the output; any other disagreement extends the run. Each arm commits run exactly once, so there is nothing for "last write wins" to decide.
  • Two streams. state is the row-per-edge debug stream. flip records only the interesting moments. Keeping them apart lets a host listen to flip alone.

The bench plays the finger. Its three timed reactions are the stimulus: the button starts low, bounces high at 2.0 ms, low at 2.2 ms, and high for good at 2.4 ms. Three reactions may commit to the same signal because they are in the same module. The clock is 1 kHz, so it samples at 0.5, 1.5, 2.5 ms and so on, and never sees the bounce:

A complete example: a PWM generator

A counter that wraps every period clocks, and an output that is high while the count is below a duty word. Two details make it a good PWM: the duty word is latched once per cycle, so a change never splits a pulse, and the output is a register, so it never glitches.

/// A free-running clock.
module Osc(out clk: Bit = false) { f: f64 = 1M where f > 0.0; }
digital for Osc { on clk.changed() { clk <- !clk after 0.5 / f; } }

/// Counter-based PWM: `period` clocks per cycle, high for `duty` of them.
module Pwm(in clk: Bit, in duty: Bit, out pwm: Bit = false, out wrap: Bit) {
    period: u8 = 100 where period >= 2;
    signal count: Bit = 0;
    /// The duty word in use for this cycle.
    signal width: Bit = 0;
    wrap = count == 0;                          // a definition: high during the first count
}
digital for Pwm {
    on clk.rise() {
        let last = count == period - 1;
        let next = if last { 0 } else { count + 1 };
        let w = if last { duty.known_or(0) } else { width };    // latch at the wrap
        count <- next;
        width <- w;
        pwm <- next < w;
        if last { emit!("cycle", t = now(), duty = w); }
    }
}

/// The bench: 25 % duty, changed to 60 % in the middle of the third cycle.
module PwmBench() {
    signal clk: Bit;
    signal duty: Bit = 25;
    pub signal pwm: Bit;
    signal wrap: Bit;
    let osc = Osc(clk) { f: 1M };
    let pulse = Pwm(clk, duty, pwm, wrap) { period: 100 };
}
digital for PwmBench {
    on at(250u) { duty <- 60; }
}

The pattern in this reaction is worth copying. First compute everything the next state needs into locals (last, next, w), from the current state. Then commit. Because the output is computed from next and w, not from count and width, pwm changes in the same microstep as the counter it belongs to.

wrap is a definition, so it has no initial value of its own: it is always count == 0. With a 1 MHz clock the PWM runs at 10 kHz, and the cycle stream has one record per period carrying the duty word that period will use. The bench changes duty from 25 to 60 at 250 µs, in the middle of a cycle, and the stream shows the change taking effect at the next wrap, never earlier.

From print to check

Once a debug print has shown you what "right" looks like, turn it into a check. The library's require(name, pass) is a function over emit! that writes a record to the reserved checks stream; the host reports each one as a pass or a failure, and an unknown pass is reported as unknown, never as a pass. finish() writes to the reserved sim stream and ends the analysis at that instant.

/// Checks a PWM from outside: the duty in use never exceeds a limit, and stops after `cycles`.
module PwmCheck(in clk: Bit, in wrap: Bit, in pwm: Bit) {
    limit: u8 = 90;
    cycles: u32 = 20;
    signal high: Bit = 0;       // high clocks seen in this cycle
    signal seen: Bit = 0;      // cycles completed
}
digital for PwmCheck {
    on clk.rise() {
        if wrap {
            require("duty_limit", high <= limit);
            high <- if pwm { 1 } else { 0 };
            seen <- seen + 1;
            if seen + 1 >= cycles { finish(); }
        } else if pwm {
            high <- high + 1;
        }
    }
}

Place it beside the generator in PwmBench with let chk = PwmCheck(clk, wrap, pwm);. A check is an ordinary reaction: it runs when its event fires and reads what any reaction reads. The library also has ready-made monitors built this way, such as Never(clk, bad) and Setup(clk, d) { ts: 100p }; chapter 10 lists them.

Walkthrough: a flip-flop with async reset

module Dff(in clk: Bit, in rst_n: Bit, in d: Bit, out q: Bit) { reset: T; }
digital for Dff {
    on clk.rise() || rst_n.fall() { if !rst_n { q <- reset; } else { q <- d; } }
}
  1. Drives. Dff holds the one drive of q, by commits. q has no initial value, so it starts unknown.
  2. Events. If the clock rises and reset falls together, the reaction still runs once.
  3. Reset low from the start. The first value of rst_n is a change from unknown to low, so fall() fires at time 0 and q takes reset one microstep later.
  4. A clock edge. The reaction reads rst_n and d as settled in that microstep; the commit applies in the next.
  5. Unknown rst_n. Both arms run and their commits merge level by level, so q keeps the levels on which reset and d agree. If you want Verilog's behavior instead, write if !rst_n.known_or(true).

Pipelines fall out of "reads see the past". One reaction can describe all three stages of a multiply-accumulate pipeline, in any statement order, because every right-hand side reads the registers as they were before the edge:

module MacPipe(in clk: Bit, in a: Bit, in b: Bit, in valid_in: Bit,
               out acc: Bit = 0, out valid_out: Bit = false) {
    signal a1: Bit;
    signal b1: Bit;
    signal v1: Bit = false;
    signal p2: Bit;
    signal v2: Bit = false;
}

digital for MacPipe {
    on clk.rise() {
        a1 <- a; b1 <- b; v1 <- valid_in;                    // stage 1
        p2 <- (a1 as i32) * (b1 as i32); v2 <- v1;           // stage 2
        if v2 { acc <- acc + p2 as i40; } valid_out <- v2;   // stage 3
    }
}

Chapter 8

Mixed-signal

Goal

By the end of this chapter you can connect the two worlds in both directions: a comparator with hysteresis that feeds a counter, and a small closed loop, a buck converter whose digital controller samples an analog output and steers a power stage. You will be able to say, for any record in your debug streams, which analog solution it saw.

Mixed-signal in MSL is not a separate sublanguage. One module can have an analog block and a digital block, and they share the module's names. You have done it since chapter 1: Step had both. Two rules connect the worlds:

  • Analog reads digital through known_or, known or high(). A digital carrier is a constant of each solve. When it changes, the analog side sees a jump and is solved again.
  • Digital reads analog by probing in a reaction, or by an event on an analog expression: above(v(vin) - vth). A crossing is located in time by the solver.

A complete example: counting the cycles of a sine

Turn a sine wave into pulses and count them. The analog-to-digital step is a comparator with hysteresis: it switches high above one threshold and low below a lower one, so a noisy input that lingers near the threshold cannot make it chatter. The library has it as A2D, and its whole source is four lines:

module A2D(a: Electrical, out d: Bit = false) { vth: f64 = 0.6; hyst: f64 = 50m; }
digital for A2D {
    on above(v(a) - vth - hyst / 2.0) { d <- true; }
    on above(vth - hyst / 2.0 - v(a)) { d <- false; }
}

Two reactions, each on a crossing: the first fires when v(a) rises through vth + hyst/2, the second when it falls through vth − hyst/2. Here is the complete design around it:

/// A sine voltage source.
module Vsin(p: Electrical, n: Electrical) { amp: f64 = 1.0; f: f64 = 1k where f > 0.0; }
analog for Vsin {
    v(p, n) +> amp * (2.0 * PI * f * now()).sin();
    bound_step(0.02 / f);
}

/// Counts rising edges of `pulse`.
module EdgeCounter(in pulse: Bit, out count: Bit = 0) {}
digital for EdgeCounter {
    on pulse.rise() {
        count <- count + 1;
        emit!("pulse", t = now(), n = count + 1);
    }
}

module CycleCounter() {
    signal vin: Electrical;
    signal hit: Bit;
    pub signal count: Bit;
    let src = Vsin(vin, gnd) { amp: 1.0, f: 1k };
    let cmp = A2D(vin, hit) { vth: 0.0, hyst: 0.2 };
    let ctr = EdgeCounter(hit, count);
}

The node vin goes to the converter's electrical port; the converter's Bit output goes to the counter. Nothing else connects the two worlds. With a threshold of 0 V and 0.2 V of hysteresis, the comparator goes high when the sine rises through +0.1 V, which first happens 15.9 µs into each period:

The times are not multiples of the solver's step: each one is the located crossing. And the microstep is 2, not 0. That number is the story of the instant, which is the next section.

The instant

Time in MSL is a pair (t, n): a real time and a microstep. At one time, microsteps run until nothing is pending. For a time the solver lands on, the analog side is solved once, the first time the digital side goes quiet; a change made after that is seen by the next step.

This is the question behind every mixed-signal debug print, and the answer has two cases.

settlethe solution at this time, with the final digital statean oscilloscope: one sample per time point

The first row is why a flip-flop that samples a comparator output on the same instant gets the old value, as hardware does. A reaction that probes also makes its time a time point: the solver lands on it exactly instead of stepping across it. The opposite also holds: a change to a digital carrier that analog does not read is not a jump, and the analog solution is not recomputed for it. Falling clock edges that nothing listens to cost the solver nothing.

A comparator without hysteresis

When you want the plain comparator, name the two crossings in the body and react to either:

/// Comparator, right from the operating point: the event says which way it went.
module Comparator(inp: Electrical, inn: Electrical, out q: Bit = false) {
    ttol: f64 = 1p;
    let up = above(v(inp, inn), ttol);
    let dn = above(-v(inp, inn), ttol);
}
digital for Comparator { on up || dn { q <- up; } }

let up = above(…); places one crossing detector and names it. In the head, up || dn fires on either; in the body, up read as a bool says whether it was the rising one. ttol is how precisely the solver must locate the crossing in time.

Between modules: converters

Across a module boundary, a Bit and an Electrical never connect. You place a converter from the standard library, and so the electrical details of every crossing are a visible, named instance with params: A2D is the threshold with hysteresis above; D2A drives a level through an output resistance with finite edges; Bidir is a pad on a Wire.

module D2A(in d: Bit, a: Electrical, vdd: Electrical) {
    rout: f64 = 100.0; tr: f64 = 20p;
    let ramp = transition(match d.known() { Some(true) => 1.0, Some(false) => 0.0, None => 0.5 }, 0.0, tr, tr);
}
analog for D2A { i(a) +> (v(a) - ramp * v(vdd)) / rout; }

Look at how it treats an unknown input: d.known() gives three cases, and the model drives half the supply for "don't know". That is the choice E0150 forces every analog reader to make. transition turns the stepped level into a ramp of duration tr, so the output has a real edge.

A complete example: a buck converter's control loop

Now close a loop through both worlds. A buck converter steps 12 V down to 3.3 V by switching: a high-side switch connects an inductor to the input for a fraction d of each period, and the output settles near d · 12 V. A digital controller measures the output once per period and adjusts d. This is a simplified version of a real digital controller: one integrator instead of a full compensator, and a pulse timed directly instead of a counter-based PWM.

module Resistor(p: Electrical, n: Electrical) { r: f64 where r > 0.0; }
analog for Resistor { i(p, n) +> v(p, n) / r; }

module Capacitor(p: Electrical, n: Electrical) { c: f64 where c > 0.0; }
analog for Capacitor { i(p, n) +> ddt(c * v(p, n)); }

module Inductor(p: Electrical, n: Electrical) { l: f64 where l > 0.0; }
analog for Inductor { v(p, n) +> ddt(l * i(p, n)); }

module Vdc(p: Electrical) { dc: f64 = 1.0; }
analog for Vdc { v(p) +> dc; }

/// A switch: `ron` while `ctl` is high, `roff` otherwise.
module RSwitch(a: Electrical, b: Electrical, in ctl: Bit) { ron: f64 = 50m; roff: f64 = 1M; }
analog for RSwitch { i(a, b) +> v(a, b) / if ctl.high() { ron } else { roff }; }

/// Half bridge and LC filter. `hs` high connects the switch node to `vin`, low to ground.
module PowerStage(vin: Electrical, vout: Electrical, in hs: Bit) {
    l: f64 = 22u;
    c: f64 = 100u;
    pub signal sw: Electrical;
    let high = RSwitch(vin, sw, hs);
    let low = RSwitch(sw, gnd, !hs);
    let ind = Inductor(sw, vout) { l };
    let cap = Capacitor(vout, gnd) { c };
}

/// The controller. Once per switching period it samples `vout`, integrates the error
/// into the duty cycle and starts a high-side pulse of that width.
module BuckControl(vout: Electrical, out hs: Bit = false) {
    vref: f64 = 3.3;
    fsw: f64 = 100k where fsw > 0.0;
    /// Integral gain: change of duty per volt of error, per period.
    ki: f64 = 1m where ki > 0.0;
    signal duty: Bit = 0.0;
    let tick = every(0.0, 1.0 / fsw);
}
digital for BuckControl {
    on tick {
        let err = vref - v(vout);
        let d = (duty + ki * err).clamp(0.0, 0.9);
        duty <- d;
        hs <- true;
        hs <- false after d / fsw;
        emit!("loop", t = now(), vout = v(vout), err = err, duty = d);
    }
}

module Buck() {
    signal vin: Electrical;
    pub signal vout: Electrical;
    signal hs: Bit;
    let supply = Vdc(vin) { dc: 12.0 };
    pub let power = PowerStage(vin, vout, hs);
    let load = Resistor(vout, gnd) { r: 3.3 };
    let ctl = BuckControl(vout, hs);
}

The power stage is a netlist you can already read, with one new trick: RSwitch(sw, gnd, !hs) passes an expression to an in port. The low-side switch is driven by the complement of the high-side command, with no extra signal.

The controller is where the two worlds meet. Line by line:

  1. let tick = every(0.0, 1.0 / fsw); places a periodic event: time 0, then every 10 µs. It is an instance, so it is named in the body and read in the reaction's head.
  2. let err = vref - v(vout); is the analog-to-digital crossing: a probe inside a reaction. The tick is a scheduled time, so by the table above the probe reads the output as it was just before the tick. That is a sample-and-hold, written in one expression.
  3. let d = (duty + ki * err).clamp(0.0, 0.9); is the integrator: the old duty plus a small step in the direction of the error, limited to a safe range. duty is a Bit<f64>: a real number that changes only at events.
  4. hs <- true; hs <- false after d / fsw; is the pulse. Two commits from two statements: one raises the command at the next microstep, the other lowers it d periods later. This is the digital-to-analog crossing: RSwitch reads hs in its analog block, so each edge is a jump and the solver lands on it.
  5. emit!("loop", …) is the window into the loop: one record per period with the sample, the error and the duty just decided. duty = d prints the new value; duty = duty would print the old one.

Run a transient and the loop stream is the start-up of the converter, period by period:

stream Buck.ctl.loop
  instant         fields
  (0, 1)          t = 0        vout = 0.000   err = 3.300   duty = 0.0033
  (10 µs, 0)      t = 1.0e-5   vout ≈ 0.000   err ≈ 3.300   duty ≈ 0.0066
  (20 µs, 0)      t = 2.0e-5   vout ≈ 0.000   err ≈ 3.300   duty ≈ 0.0099
  …                            the duty climbs, the output follows
  (≈ 8 ms, 0)                  vout ≈ 3.300   err ≈ 0.000   duty ≈ 0.28

You can check the ends of it by hand. At the start the output is zero, so each period adds ki · 3.3 = 0.0033 to the duty. At the end the error is zero and the duty sits where 12 V times the duty, less the small drop in the switch, equals 3.3 V: about 0.28. What happens in between, how fast the loop settles and whether it rings, is what the stream is for. Plot vout against t from the records and you have the loop's step response without touching a waveform viewer.

With the print in place, the acceptance test is one more reaction in the top. It checks, at every time point after start-up, that the output stays within 50 mV of the target:

digital for Buck {
    on settle {
        if now() > 10m { require("regulated", (v(vout) - 3.3).abs() < 50m); }
    }
}

Walkthrough: a first-order delta-sigma modulator

One module, both blocks: an integrator in continuous time, a one-bit quantizer sampled by a reaction, and feedback through a digital carrier.

module DeltaSigma1(vin: Electrical, in clk: Bit, out bit: Bit = false) {
    r: f64 = 100k; c: f64 = 1p; vref: f64 = 1.0;
    signal x: Electrical = 0.0;
}

analog for DeltaSigma1 {
    let fb = if bit.high() { vref } else { -vref };
    i(x) +> ddt(c * v(x)) - (v(vin) - fb) / r;
}

digital for DeltaSigma1 {
    on clk.rise() { bit <- v(x) > 0.0; }
}
  1. The equation. x has one branch, so KCL gives c · dv(x)/dt = (v(vin) − fb) / r.
  2. Start. In an equilibrium solve ddt is zero, so x has no DC path. Its = 0.0 holds it at 0 V through the transient's operating point. On the first step the hold is released, with no jump.
  3. A rising clock edge at (t, 0). The reaction probes, so t is a time point. It reads v(x) as it was just before the edge and commits bit.
  4. At (t, 1). If bit changed, analog reads the change: a jump. The capacitor charge stays; the feedback current steps by 2 · vref / r.
  5. Falling edges fire no reaction, and analog never reads clk, so they cost the solver nothing.
  6. DC, AC and noise. Outside a transient's operating point nothing is held, so a Dc solve is singular and names x. That is the truth about an integrator with no DC path. Ac and Noise fail the same way; the loop's response needs a periodic analysis.

To watch the modulator, add emit!("q", t = now(), x = v(x), bit = v(x) > 0.0); to the reaction: one record per clock with the integrator's value and the decision taken from it.

Bigger systems are just composition. A SAR ADC places a sample-and-hold, a DAC, the Comparator above and a binary-search state machine, and adds one branch of its own on a public node of its DAC:

module SarAdc(vin: Electrical, in clk: Bit, in start: Bit, out code: Bit, out done: Bit) {
    cpar: f64 = 50f;
    signal vh: Electrical;
    signal vdac: Electrical;
    signal cmp: Bit;
    let sh = SampleHold(vin, vh, start);
    let dac = Dac8(code, vdac);
    let comp = Comparator(vh, vdac, cmp);
    let logic = SarLogic(clk, start, cmp, code, done);
}
analog for SarAdc { i(dac.core) +> ddt(cpar * v(dac.core)); }    // the parent's own branch on a public node

Good to know

The guidance in short: read a digital carrier in analog only when the analog behavior depends on it; prefer known times (at, after, every) to crossings; sample at a clock edge with a reaction, not with cross on the clock's analog image; give edges a duration with transition when edge rate matters.

Chapter 9

Files, modules and packages

Goal

By the end of this chapter you can split a design over several files, share modules between them with mod, use and pub, write the manifest of a package, and depend on someone else's package.

Until now every example was one file. Real designs are not, and MSL organizes code the way Rust and Cargo do, without exceptions: files are namespaces, a tree of files is a crate, and a directory with a manifest is a package. If you know Cargo, you know this chapter; read the example and the differences.

A complete example: one design, three files

Take the RC low-pass of chapter 1 and give it a proper home. The parts go in one file, the filter built from them in another, and the crate root declares both and holds the top.

lowpass/
├── Piperine.toml
└── src/
    ├── lib.msl            the crate root
    ├── parts.msl          mod parts;
    └── filter.msl         mod filter;
// src/parts.msl
/// Ideal resistor.
pub module Resistor(p: Electrical, n: Electrical) { r: f64 where r > 0.0; }
analog for Resistor { i(p, n) +> v(p, n) / r; }

/// Ideal capacitor.
pub module Capacitor(p: Electrical, n: Electrical) { c: f64 where c > 0.0; }
analog for Capacitor { i(p, n) +> ddt(c * v(p, n)); }

/// A constant voltage on `p`, referred to ground.
pub module Vdc(p: Electrical) { dc: f64 = 1.0; }
analog for Vdc { v(p) +> dc; }
// src/filter.msl
use crate::parts::{Capacitor, Resistor};

/// First-order low-pass with corner frequency `fc`.
pub module LowPass(a: Electrical, b: Electrical) {
    fc: f64 = 1k where fc > 0.0;
    r: f64 = 1k where r > 0.0;
    let r1 = Resistor(a, b) { r };
    let c1 = Capacitor(b, gnd) { c: 1.0 / (2.0 * PI * r * fc) };   // the capacitor of this corner
}
// src/lib.msl
pub mod parts;              // loads src/parts.msl
pub mod filter;             // loads src/filter.msl

use crate::filter::LowPass;
use crate::parts::Vdc;

/// The top: a source and the filter.
pub module Bench() {
    signal vin: Electrical;
    pub signal vout: Electrical;
    let src = Vdc(vin) { dc: 1.0 };
    pub let lp = LowPass(vin, vout) { fc: 10k };
}
[package]
name = "lowpass"
version = "0.1.0"

[run.op]
analysis = "op"

What each new line does:

  • pub mod parts; in the crate root declares a namespace and loads it from parts.msl. A file that no mod names is not part of the crate.
  • pub module Resistor makes the module visible outside its file. Without pub it is private to parts.
  • use crate::parts::{Capacitor, Resistor}; brings two names into scope. crate is the root of this crate.
  • analog for Resistor stays next to module Resistor. This is the one rule MSL adds to Rust's: a hardware module and all its behavior blocks are in the same file, so you never hunt for the equations of a device.
  • The manifest needs only a name and a version. std is not listed: every crate has it. The [run.op] table is for the command line: a run with no bench key takes its top from the library itself.

Splitting a design changes nothing about its instances: the capacitor is still Bench.lp.c1, and a stream written inside the filter is still named under Bench.lp. Paths of instances follow the hierarchy of the design, not the files it is written in.

No search paths, no textual include, no macros

A crate reaches another crate only through a dependency named in its manifest. No implementation may find one through a search path, a registry or an environment variable. There is no -I and no package registry. There is no textual include of source either: code is shared through mod and use, and the only ! forms are emit! and include_str!.

include_str! is for data. It is allowed only in a const initializer, its path is relative to the source file, and the file is read once, at elaboration. A run never opens a file:

const IV:  [(f64, f64); 64] = parse_table(include_str!("diode_iv.tbl"));   // whitespace columns
const ROM: [u32; 1024]      = parse_hex(include_str!("boot.hex"));         // $readmemh format

module MeasuredDiode(a: Electrical, k: Electrical) {}
analog for MeasuredDiode { i(a, k) +> table_model(v(a, k), &IV, "3E"); }   // cubic, error outside

The standard library and the prelude

std is a crate that ships inside Piperine. Every crate depends on it, no manifest names it, and no dependency may be called std. The prelude, the pub items of std::prelude, is implied in every file, which is why Bit, Electrical, idt and above need no use. A handful of core names need nothing at all: gnd, Nature, m, dtemp, str and the core primitives like ddt and cross. Chapter 10 tours both.

When names collide

The first segment of a path is looked up in this order, and the first hit wins:

  1. the enclosing blocks and declarations;
  2. the items and imports of the enclosing namespace;
  3. the dependency names of the crate;
  4. the prelude;
  5. the core names.

So in an ordinary path, a local item beats a dependency of the same name, silently. In a use, the same clash is an error, never a silent choice:

mod util;                  // a local namespace called util
use util::cells::Cell;     // E0163: the local `util` or the dependency `util`?

Only a name that can head a path clashes: a namespace, a type, a nature or a module, as in Rust. A local fn util or const util lives in the value namespace, so util::cells::Cell still reaches the crate.

Two ways out: rename the dependency in the manifest, or name the local one through crate.

[dependencies]
utilx = { path = "../util", package = "util" }    # now `utilx::cells::Cell`
use crate::util::cells::Cell;   // the local namespace, unambiguous

Chapter 10

Core and standard library

Goal

By the end of this chapter you know where every name you did not declare comes from, you can find the library module for a job instead of writing it again, and you have a small debugging kit built from emit!, log, require and fatal.

This chapter is a tour, not a lesson: read the first two parts, then skim the tables and come back when you need a name. Each part has one small module that uses a few of its names, and every one of those modules is a complete file.

Every name you write in a model comes from one of three places: your own files, the core, or the standard library. The core is what only the simulator can provide: reading a voltage, taking a time derivative, locating a crossing. Everything else, idt, transition, Wire, Setup, is ordinary source code written in the language, shipped as the crate std, and you can open it and read it. This chapter is the tour that tells you which is which.

Together with your own streams they make a debugging kit. This watchdog uses three of them: a record with the numbers, a message, and an end to a run that is going nowhere.

/// Ends the run when `busy` stays high for more than `limit` clock edges.
module Watchdog(in clk: Bit, in busy: Bit) {
    limit: u16 = 1000;
    signal run: Bit = 0;
}
digital for Watchdog {
    on clk.rise() {
        if !busy.known_or(true) {
            run <- 0;
        } else if run >= limit {
            emit!("stuck", t = now(), edges = run);
            fatal("busy was never released");
        } else {
            run <- run + 1;
        }
    }
}

An unknown busy is read as high, the pessimistic choice for a watchdog. The stuck record carries the time and the count; fatal ends the analysis at that instant and marks it failed. Had the condition itself been unknown, the sim record would carry maybe = true and the run would go on: an analysis is never ended on a guess.

When errors happen

A worked example: three errors in one file

Here is a first attempt at the sample-and-hold of chapter 3, written the way a newcomer would. It parses, so the listing below is legal syntax, and it has three mistakes that elaboration finds.

module SampleHold(vin: Electrical, vout: Electrical, clk: Bit) {

    on clk { held <- v(vin); }
}

Chapter 12

The object model

Goal

By the end of this chapter you know what a tool sees when it reads your source, and you can ask a design questions from Rust: which ports a module has, where a signal is declared, and who writes it.

Everything so far was about writing models. This chapter is about reading them by program. You need it when you build a tool, and it helps even when you do not, because it is the precise version of a question you ask all the time while debugging: "who drives this signal?"

The Piperine Object Model, the POM, is the in-memory model of a set of MSL sources. One call turns source text into an immutable Design, and every later stage starts from it: a type checker, an elaborator, the simulator front end, an editor. It is the Rust library piperine_lang::pom, and it reads the way Java reflection does. You ask a module for its ports, a signal for the module it is declared in, an instance for the module it places.

The promise: it mirrors your source

The POM's navigability mirrors the source. What you read back from a Design is the structure the author wrote.

Modules, instances and hierarchy come back as you wrote them. A generation for stays one for, never unrolled; a let stays a let. Name resolution only adds links between nodes. Anything that needs another shape, such as flattening, is a separate artifact built from the design. You never have to reverse-engineer an elaborator to find your own module.

sources ──► parse ──► lower ──► resolve ──► index ──► Design
(text)      syntax    arenas    names,       reverse   (immutable,
            tree      of nodes  classes,     tables    Send + Sync,
                                members                serializable)

A short tour

Take Front, a comparator with hysteresis that drives a flip-flop:

/// A comparator with hysteresis that drives a flip-flop.
module Front(vin: Electrical, in clk: Bit, out q: Bit) {
    vth: f64 = 0.6;
    hyst: f64 = 50m;
    signal above_th: Bit = false;        // state: a signal
    signal d: Bit;
    d = above_th;                        // structure: a combinational definition
}

digital for Front {
    on above(v(vin) - vth - hyst / 2.0) { above_th <- true; }    // an analog event
    on above(vth - hyst / 2.0 - v(vin)) { above_th <- false; }
    on clk.rise() { q <- d; }                                    // a digital event
}

With the design built, you ask it questions in Rust. These lines are from the POM's own tour:

// The structure is what was written, by name.
let front = design.module("Front").unwrap();
let ports: Vec<_> = front.ports().iter().map(|p| p.name().unwrap()).collect();
assert_eq!(ports, ["vin", "clk", "q"]);
assert_eq!(front.params().len(), 2);
assert_eq!(front.signals().len(), 2);

// A signal knows where it is declared.
let d = front.signal("d").unwrap();
assert_eq!(d.declared_in().unwrap().name(), Some("Front"));
assert_eq!(d.qualified_name(), "Front.d");

// The `above(..)` calls are instances of a module, and the behavior block belongs to `Front`.
assert_eq!(front.instances().len(), 2);
let block = &front.digital_blocks()[0];
let events: Vec<_> = block.reactions().iter().map(|r| r.event().text()).collect();
assert_eq!(events[2], "clk.rise()");

// Reverse queries: who writes `d`, and who writes `q`.
assert_eq!(d.writers().len(), 1);                        // the definition `d = above_th;`
assert_eq!(front.port("q").unwrap().writers().len(), 1); // the commit `q <- d;`

What it is and is not

  • Always builds. build() returns a Design however broken the input. Parse errors keep the recovered tree and go to diagnostics(), sorted by file, offset and code.
  • Lossless. Every file keeps its text and syntax tree, and the tree can be rebuilt from the POM alone, spans included.
  • A plain value. A Design is Clone, comparable with ==, Send + Sync and serializable to JSON.
  • No type checking, evaluation, elaboration or simulation. Constants and where clauses stay expressions; generics are not instantiated. The POM says what was written and what each name refers to.
  • No mutation. Edit the source and build again.

With packages, a design is built over a graph of crates, each kept as authored, and names resolve across crates by the rules of chapter 9.

Chapter 13

Device ABI

Everything the solver simulates is a device, and every device meets the solver through one binary interface, the device ABI. A resistor compiled from MSL, a BSIM model compiled to OSDI, an AVR microcontroller emulator, the IR interpreter running a model nobody compiled: the solver calls all of them the same way. You never write against it when you write MSL; the compiler does. This chapter is for when you want to know what your module becomes, or to plug in a device that was not written in MSL.

Status

Built. The ABI lives in the crate piperine-abi, which has no dependencies and is the only crate a device links against. The solver calls every device through it; the old per-kind device interfaces are gone. Its design was settled by an adversarial review: a builder and a critic went four rounds, and its elegance score rose from 5.5 to 8.1 with no blocker left.

Why one ABI

A simulator usually grows one interface per kind of model: one for compiled analog models, one for digital primitives, one for co-simulation, each with its own hooks for setup, temperature, checkpoints and rollback. Piperine has one. The solver calls every device through the same pointers, whether the library came from dlopen (generated Rust, C, an OSDI adapter, an emulator) or lives in the same process (the IR interpreter, a test element, a host stimulus). A bug in coupling is fixed once, for all of them.

The idea, in five points

  1. A device is a shape plus two kinds of code. The shape is plain data describing the instance. The code is functions, which are pure (bytes in, bytes out, with partial derivatives), and reactions, which run at an instant and whose only effect is a commit.
  2. The device has no memory. Everything that exists over time lives in the solver: unknowns, discrete values, pending commits, integrator and delay histories, limiter iterates. State a device needs is a private pin, just as state in MSL is a signal. So checkpoint, rollback and replay need no entry point.
  3. A pin is the only shared thing. A pin is a net seen from an instance, and it obeys the net rules without exception. Ports, internal nodes, branch flows, signals, state, params, temperature, timers, crossings, settle, records: all pins.
  4. Four analog cells. What is not a net is an input or an output of a call. A term is a value added to a row, through one of three operators: 1, d/dt or delay. A held input is a value the solver supplies and perturbs (a limiter iterate, a noise source, an AC stimulus). An ambient input is a coordinate of the call (the time, the frequency, the horizon). A watch is an analog output that enters no row (a crossing, a step cap, an operating-point variable).
  5. One rule runs all code. A function runs when the solver needs one of its outputs and one of its inputs changed. A reaction runs when an event pin it listens to fires.

The device says only what a value is. A capacitor says "this is a charge"; equilibrium, TR-BDF2, the truncation test, jω·c in an AC sweep and the history across an undone step are the solver's business.

The Rust side

In Rust a device is a type that implements one trait. No macro is involved: a generic function produces the C thunks.

pub trait Device: Sized + Send + 'static {

    fn eval (&self, k: u32, cx: &mut Eval<'_>)  -> Result<(), Fault>;

pub const fn module(name: &'static str) -> Module;       // generic extern "C" thunks; no macro

Eval and React are borrow-checked views over the call's buffers: cx.f64(i) and cx.bytes(i) read input i, cx.set(j, v) writes output j, cx.jac() is the partials, cx.commit(statement, bytes, after) queues a write. A panic becomes a FAULT with its message.

Three devices

These are verbatim from the ABI document, with the partials written by hand so the contract shows. The comment above each one is its shape: reads and writes in order, partials as (write ← read). Generated code computes the partials for you.

A resistor. In MSL it is one line of behavior:

module Resistor(p: Electrical, n: Electrical) { r: f64 = 1k; }
analog for Resistor { i(p, n) +> v(p, n) / r; }

As a device it is two port pins, one param pin, one term and one function:

// pins:   p, n (PORT continuous);  r (PARAM F64, default 1e3)
// terms:  T0 FLOW {p, n} "i"
// fn 0 "i":  reads [p, n, r]   writes [T0]   partials (0←0) (0←1) (0←2)
fn eval(&self, _k: u32, cx: &mut Eval) -> Result<(), Fault> {
    let (v, r) = (cx.f64(0) - cx.f64(1), cx.f64(2));
    cx.set(0, v / r);
    cx.jac().copy_from_slice(&[1.0 / r, -1.0 / r, -v / (r * r)]);    // the last matters only when seeded
    Ok(())
}

Two resistors of 1 kΩ and 2 kΩ share this shape; the solver seeds each one's param net with its value.

A D flip-flop. The MSL:

module Dff(in clk: Bit, in d: Bit, out q: Bit = false) {}
digital for Dff { on clk.rise() { q <- d; } }

The edge clk.rise() becomes a discrete function that fires a private event pin; the on block becomes a reaction listening to it; q <- d becomes one commit:

// pins: clk, d (PORT BIT);  q (PORT BIT, init LOW);  rise (PRIVATE event)
// fn 0 "rise":  reads [clk.VALUE, clk.PREVIOUS, clk.CHANGED]   writes [rise]
// reaction 0:   on [rise]   reads [d]   writes [S0 {q}]
fn eval(&self, _k: u32, cx: &mut Eval) -> Result<(), Fault> {
    cx.set(0, (cx.bytes(2) == [1] && cx.bytes(0) == HIGH && cx.bytes(1) == LOW) as u8);
    Ok(())
}
fn react(&self, _k: u32, cx: &mut React) -> Result {
    cx.commit(0, cx.bytes(0), 0.0)?;                  // q <- d : applies at (t, n+1)
    Ok(Flow::Continue)
}

An AVR emulator. Not written in MSL at all: a foreign device with its own clock, coupled through the same six entry points. Its whole CPU state is one private pin, so the solver can checkpoint and roll it back like any signal.

// pins:  pad_in[8], pad_out[8] (PORT BIT)     adc0 (PORT continuous)     reset (PORT BIT)
//        firmware (PARAM U8[256], STRUCTURAL)  f_cpu (PARAM F64)
//        cpu (PRIVATE discrete, QUIET; layout: registers, SRAM, timers, its own tick — plain fields)
//        adc_val (PRIVATE REAL)                log (PRIVATE discrete, RECORD)
//        irq, wake, sample (PRIVATE event)
//        resolution (GLOBAL RESOLUTION), start (GLOBAL START)
// fn 0 "pad change": reads [pad_in[0..8].CHANGED, reset.CHANGED, adc_val.CHANGED]   writes [irq]
// reaction 0 "run":    on [start, irq, wake]
//                      reads  [cpu, pad_in[0..8], reset, adc_val, resolution, start.CHANGED, TICK, HORIZON]
//                      writes [S0 {cpu}, S1..S8 {pad_out[i], LATER}, S9 {wake, LATER|REPLACE},
//                              S10 {sample, LATER}, S11 {log}]
// reaction 1 "sample": on [sample]   reads [adc0]   writes [S0 {adc_val}]
fn react(&self, k: u32, cx: &mut React) -> Result {
    if k == 1 { cx.commit(0, &real(cx.f64(0)), 0.0)?; return Ok(Flow::Continue); }

    let mut cpu: Cpu = *cx.get::(CPU).unwrap();           // a copy of the state pin; Cpu: Pod
    let (now, horizon, res) = (cx.i64(TICK), cx.i64(HORIZON), cx.f64(RES));
    if cx.bytes(START) == [1] { cpu = Cpu::reset(now); }
    cpu.set_pads(cx.bits(PAD_IN), cx.bytes(RESET));            // pin-change interrupts are raised here
    cpu.adc_result(cx.get::(ADC_VAL));

    // run my own clock through the horizon, or to my first externally visible action
    let stop = cpu.run(&self.flash, self.ticks_per_cycle, horizon);
    let dt = (cpu.tick - now) as f64 * res;
    match stop {
        Stop::PadWrite { pad, level } => cx.commit(1 + pad, &level, dt)?,   // the edge keeps its exact time
        Stop::AdcStart                => cx.commit(10, &[], dt)?,           // fire `sample` then
        Stop::Break { pc }            => cx.commit(11, bytes_of(&Log { pc, known: 1 }), 0.0)?,   // a record
        Stop::Horizon | Stop::Sleep   => {}
    }
    cx.commit(9, &[], cpu.next_wake(now, res))?;               // "advance me to": REPLACE re-arms
    cx.commit(0, bytes_of(&cpu), 0.0)?;                        // the state, committed like any signal
    Ok(Flow::Continue)
}
  • How far it may run. HORIZON is the last tick through which nothing it listens to or reads can change. It runs its own clock up to there, or stops earlier at its first output, because that output may come back to it.
  • "Wake me at." A commit with a delay to its private wake event pin; REPLACE re-arms it.
  • The ADC. A second reaction that reads a continuous pin, so only the samples cost an analog landing.
  • Rollback. None of its own: its state is a pin in the owner's checkpoint. An emulator that cannot expose its state marks run IRREVERSIBLE instead, and pays for it with an analog landing at every instant it fires (in a design with a crossing) and a session the host cannot rewind.

Good to know

Because a function is pure and a device holds no hidden state, a recorded call is a unit test: the same bytes through the compiled device and through the interpreter must give the same answer. In a debug session the solver also checks every Jacobian against finite differences.

What it changes in the spec

The ABI brought a few small changes to the language rules. They are now part of the specification.

  • Delayed commits do not make time points (LATER). A commit whose delay always moves time forward by at least one tick changes nothing at the instant that made it. Only its due time is tested, on its own. The one change you can observe: on settle sees fewer time points.
  • What a time point is. A time at which the analog solver produces an accepted solution and runs the time-point procedure. The simulator may accept solutions at other times; those are not time points, and settle does not fire there.
  • The C interface of an extern module is this ABI. "osdi" names the OSDI adapter; "cosim" is a module whose reaction is irreversible. A "cosim" module stays digital-only for now.
  • Two new core functions, gmin() and source_scale(), in the same family as now() and freq(). They let a model see the solver's continuation variables, as junction models in ngspice do.
  • Smaller ones. Two sentences on bytes (all-zero bytes are the all-unknown value; an unknown level's value bytes are zero), a set that would change an extern module's structure is refused like a structural param; records travel as quiet commits.

Chapter 14

The solver

The solver is the part of Piperine that turns devices into numbers. It knows physics and time, not the language: it never sees an MSL expression, only devices that speak the ABI of chapter 13. This chapter explains what it does with them, so that you can predict what a simulation will do and read what it reports.

Status

Built. The solver runs every analysis below on devices that use the ABI, with numbers bit-for-bit equal to the solver it replaced, whose results were validated against ngspice. Analog MSL designs run on it through the compiler of chapter 15, and crossings are located inside a step to the tolerances below.

Three parts, one boundary

The solver is three parts. The analog solver owns the continuous unknowns and solves the equations. The digital solver owns the discrete nets and runs instants. The event owner sits above both, owns the clock and the queue of what is due, and decides who runs when. The analog and digital solvers never call each other: everything that crosses between them is an event the owner carries.

Finding the operating point

The analog solver uses Newton's method: guess, linearize every device at the guess, solve the linear system, repeat. A solution is accepted only when two tests pass at once: no unknown moved more than its tolerance, and the currents into every node balance within tolerance. A large step is damped, and a limiter (limit in MSL) keeps an exponential junction from jumping too far.

When plain Newton fails, the solver makes the problem easier and walks back. First it adds a conductance from every node to ground and lowers it decade by decade (gmin stepping). If that fails, it turns all sources off and ramps them back up (source stepping). These are the same two steps ngspice takes, in the same order.

A mixed design alternates: solve the analog side, run the digital instant on that solution, give the analog side what changed, solve again. After 20 rounds that still change something the solver stops with E0506 and names the nets that kept moving, rather than return a wrong answer. Then settle fires once.

One transient step

Time inside the solver is an integer count of ticks (one femtosecond unless the session says otherwise), so two events at "the same time" really are at the same time. Each step goes like this:

  1. Propose. The step controller proposes how far to go, bounded by the stop time and by any bound_step.
  2. Look ahead. The digital solver runs ahead to that time. It stops at the first instant that touches the analog side, and the step is shortened to land exactly there.
  3. Solve. The analog solver integrates to that time on the values the digital side had just before the instant.
  4. Judge. If Newton failed or the error estimate is too big, everything returns to the checkpoint taken at the start, and the step is retried smaller.
  5. Locate. If a cross expression changed sign inside the step, the step is taken again, shorter, until it ends on the crossing: within etol of zero or within ttol (plus one tick) of the estimated time. The estimate is a secant through the attempts so far.
  6. Accept and react. The solution is accepted. Crossings become events, and the digital instant runs, reading the accepted solution.
  7. Deliver. What the instant changed reaches the analog side. If an analog function reads it, the next step restarts from first order, because a jump has no history to extrapolate from.

A rejected step costs only that step: no device keeps memory of its own, so going back is the solver restoring its own copies.

Integration and step size

Every ddt is integrated with TR-BDF2: each step is a trapezoidal stage followed by a second-order backward-difference stage. It is accurate like the trapezoidal rule and does not ring on stiff circuits. You never choose a method; there is only this one.

The error of each step is estimated by comparing the solution with a straight-line prediction through the two stages. A PI controller then grows or shrinks the step from that estimate, smoothly, so it does not oscillate on a stiff edge. A step that lands on a scheduled event or right after a jump is exempt from the error test, because what it measures there is the jump, not an integration error.

The digital side

One digital instant is a series of microsteps at the same time. In each, the commits due now are applied, the discrete functions that read a changed value run in dependency order, and then the reactions whose event fired run, all reading the same snapshot. Their commits are due at the next microstep, or later if they have an after. The instant ends when nothing more is due now.

  • Only what changed runs. A function whose inputs did not change is not called. A free-running clock costs only what it actually touches.
  • Combinational loops must say so. A loop of functions is accepted only if it passes through a net marked to relax, which is iterated until it stops changing. Any other loop is refused when the design is built, naming its functions.
  • Only the settled value is seen. Several commits to one net in the same microstep are applied in order and the net is written once. changed() and the previous value compare with the value before the microstep, so x <- 1; x <- 0; on a net that was 0 changes nothing.
  • Reactions see the environment. A reaction or a definition may read temperature(), gmin() and source_scale(); they get the values in force at that instant, the same ones the analog side uses.
  • An instant must go quiet. After 1000 microsteps the solver stops with E0501 and names the nets that keep changing.
  • Running ahead is safe. The digital side runs ahead of the analog side on checkpoints. If an instant turns out to touch the analog side, it is undone and becomes the next landing.

Watching and steering a run

Everything that happens can be observed as it is accepted: each value that changed, each commit, each crossing, each emit! record, and on request each Newton iteration of a function. Observations from a rejected step never reach you.

The host can change a parameter between analyses, schedule a change at a time inside a transient (the solver lands exactly there), or wait for an event and react to it. A change is first checked against the device's own rules; a refused change leaves the circuit as it was.

From source to solver

The compiler is what connects the two halves of this book: the language of chapters 1 to 12 and the solver of chapters 13 and 14. It reads your MSL, checks it, flattens the design into an intermediate form and hands the solver one device per instance. This chapter follows a source file down that path, so you know what each stage checks and where an error comes from.

Status

Built for analog circuits, with two backends. Resistors, capacitors, voltage and current sources and a diode with junction limiting run end to end from source, under operating point, DC sweep, AC and transient, through the interpreter and as compiled Rust, and every result is compared with ngspice on both. The Rust backend also runs digital and mixed-signal models from source: type checking and elaboration take definitions, carriers, events, reactions, commits, enums, match and unknown values into the intermediate form, and a full buck converter runs with its loop closed. Two backends

The intermediate form runs two ways, and they must agree bit for bit.

  • The interpreter walks a body at every call, computing values and derivatives together with dual numbers. It is simple, needs no compiler, and is the reference: every other backend is checked against it. It covers the analog forms only.
  • The Rust backend prints the whole design as one Rust source file, compiles it with the rustc it finds on the machine, and loads the library through the device ABI. It covers analog, digital and mixed forms. A design is compiled once and cached by a hash of everything that went into it, so a second run starts at once and nothing is compiled while a simulation runs. The cache entry is checked against its recorded hash before it is loaded.

Both backends compute the same function, function by function, to the last bit; the ngspice comparisons run on both. A host picks one: on the command line, --backend (rust by default, chapter 16); the test suite picks with PIPERINE_BACKEND (interp or rust) and runs both when it is unset.

Reading what runs

The generated Rust stays on disk next to the library, formatted, and is meant to be read. Every item names the MSL it came from, your names stay as you wrote them, and names the compiler makes up end in _, so they never collide with yours. Here is the resistor's analog block:

// Resistor.analog @ devices.msl:5:1
fn terms_block<R: Real>(p: R, n: R, r: R) -> [R; 1] {
    // contribution to i(p, n), branch b0 @ devices.msl:8:32
    let b0_flow_ = (p - n) / r;
    [b0_flow_]
}

The block is generic over a number type: run with plain floats it gives the current, run with dual numbers it gives the current and its derivatives, which is the Jacobian. Digital code reads the same way: a reaction is a function whose commits go out together when it ends, and an if on a value that may be unknown stops with a fault naming that if in your source.

Finding the project. A command uses the nearest Piperine.toml found upward from the directory you are in, so it works anywhere inside a project. --project <dir> names the project directly and searches nowhere else. With no manifest, a command that needs a project fails with E0170.

A bench is a module without ports that places a design with its sources, its stimulus and its monitors. It is MSL, in a file under benches/. Each bench file is the root of a small crate named bench, which depends on your package under the package's name and on each of the package's direct dependencies under theirs. So a bench of the package rc begins with use rc::…, and sees what the library marks pub.

The top. A run simulates one top module. It is the module the run's top key names, or else the one module without ports of the run's root crate: the bench file when the run has a bench, the library when it has none. If there is no such module, or more than one, the run fails with P0011 and the candidates are listed. A top may have digital in ports; they are left undriven and read as unknown. A top with an analog port is refused.

Three ways to ask for a run

piperine run step                          # the run named step, as the manifest describes it
piperine run step --stop 20e-6 --stream trip    # the same run, two settings changed
piperine run benches/delayed.msl --analysis transient --stop 5e-6    # a file, described by flags alone
  • By name. With exactly one run in the manifest the name may be left out. With none or several, or a name that is no run, the command lists the run names and exits with status 2.
  • With flags. Every key is a flag, and a flag wins over the key of the same setting. Nothing is written back to the manifest.
  • A lone file. A file run by its path needs at least --analysis. Where the file is decides what it is: with no Piperine.toml above it, it is a crate by itself; inside a project but outside src/, it is a bench of that project; under src/ it is refused, because it is already part of the library. The header shows the file's name without its extension as the run's name.

With print_step, an analog value is interpolated linearly between the two solver steps around the row's time, and a digital value is the one it held at that time. Use it whenever a run takes many steps: the solver's own steps are still all computed, and all drawn by --plot.

A long run with many unknowns can hold more steps than you want in memory. from keeps only the end of it: the solver integrates from 0 as always, and the result keeps the steps at or after from. What you can print. A node gives its voltage, a digital signal its value, and i(<instance>) the current through an instance such as a source. Each is named by its path, written in full or relative to the top: vout and Step.vout are the same signal. A column is always headed by the full path. With no print, the table shows the top module's own signals and ports, in the order they are declared.

How values are written. A real has six decimals and an exponent, 7.500000e0; a bool is true or false; an integer is decimal; an unknown value is x; a text field is in double quotes. The same input gives the same characters every time: nothing on this output depends on the clock, on your directories or on what was cached.

Records: your emit!, live

emit! is the print statement of MSL, and the command line is where its output lands. The monitor of the RC bench has one in its reaction:

digital for Monitor {
    on cross(v(a) - level) {
        emit!("trip", v = v(a));
        require("crossed_upward", v(a) >= level);
    }
}

Every emit! executed by a reaction prints one line, the moment the record is written:

@   = = …

For the monitor that is this line of piperine run step: the time of the crossing, the instance mon under the top Step, the stream trip and the one field v.

@6.931075e-7 Step.mon trip v=5.000000e-1

The fields come in the order you wrote them. Lines appear in the order the records are written, never one from a later time before one from an earlier time, and all of them before the table. The two reserved streams, sim and checks, print like any other, with one exception: a checks record whose pass is true is not printed unless you give --all-checks (or all_checks = true in the run table), because a monitor that checks every clock edge would bury everything else. A failing check, or one whose pass is unknown, always prints. The instance shown is the one whose reaction made the call. A design with no emit! prints no record line.

@6.931075e-7 Step.mon trip v=5.000000e-1

Tables and plots as files

  • --csv file writes the table as CSV: a header row with the column names, cells separated by commas, numbers written as on the terminal. In place of the table the command prints wrote <file> (<n> rows).
  • --plot file.svg writes one SVG picture and prints wrote <file> after the table. The horizontal axis is the time, the swept param or the frequency. Every printed real signal is a curve on one shared axis, with a legend; every digital signal is a step trace in a lane of its own below. An ac run gets two panels, magnitude in dB over phase in degrees, with a logarithmic frequency axis when the grid is per_decade. A curve breaks where a value is unknown. An operating point has nothing to plot.
  • Paths. A relative csv or records path is taken from the project directory, or from the directory you are in for a lone file. An existing file is replaced.

Params for one run

A param of any instance can be set before the analysis, by its path:

piperine run step --param r1.r=2200 --param c1.c=2.2e-9

The entries of the params key are applied first, then the flags, in the order given. A path that names nothing is E0801. A value the design refuses, such as one that fails the param's where, is E0802: no analysis runs. The same paths serve --sweep in a DC sweep.

Two backends

A run executes on one of two backends, and the header says which. rust, the default, turns the design into Rust and compiles it; it runs everything. interp interprets the design directly and starts at once, for analog designs; given a design it does not run, it says so and names --backend rust. For a design both run, the two are expected to print the same table.

The choice is made by the first of these that is present: the flag --backend, the environment variable PIPERINE_BACKEND, the run's backend key; otherwise rust.

The Rust backend needs a Rust compiler installed. The first run of a design compiles it and says so on the error output; the result is cached, and a run never compiles during an analysis.

A bigger project: the buck converter

The RC project is a toy. The same commands run a full-size design: a digitally controlled buck converter that steps 12 V down to 0.8 V, with an analog power stage, a 200 MHz digital PWM, an ADC, a fixed-point PID, a soft start and a supervisor, all in MSL. It is the bigger sibling of the converter of chapter 8, and a package like any other: the library buck under src/, one bench file, and two runs.

The bench, benches/startup.msl, plays the host that brings the converter up: it writes the setpoint, then raises en. A second bench in the same file holds en low.

//! The closed-loop start of the buck converter, as two benches over the package: `Startup`
//! writes the setpoint code 0 (0.8 V) and then raises `en`, with Vin 12 V into the 6.6 ohm load
//! of `Buck`'s defaults; `Idle` never raises `en`, so the supervisor stays `Off`.
use buck::dpwm::Osc;
use buck::top::Buck;
use buck::{Fault, Mode};

/// The host's two writes, on a 1 MHz clock (rising at 0.5 us, 1.5 us, ...): `sp_wr` rises at the
/// first edge with `sp_data` 0 already presented (the setpoint register takes it on the rising
/// `wr`), and `en` rises at the second.
module Host(in clk: Bit, out sp_wr: Bit = false, out en: Bit = false) {
    signal n: Bit = 0;
}
digital for Host {
    on clk.rise() {
        let s = n.known_or(0);
        if s < 2 { n <- s + 1; }
        if s == 0 { sp_wr <- true; }
        if s == 1 { en <- true; }
    }
}

/// The start: 128 samples of soft-start ramp, 64 of power-good delay, then regulation.
module Startup() {
    signal clk: Bit;
    signal en: Bit;
    signal sp_wr: Bit;
    signal sp_data: Bit = 0;
    signal load_step: Bit = false;
    signal inject: Bit = false;
    signal pgood: Bit;
    signal fault: Bit;
    signal mode: Bit;
    let osc = Osc(clk) { f: 1M };
    let host = Host(clk, sp_wr, en);
    pub let buck = Buck(en, sp_wr, sp_data, load_step, inject, pgood, fault, mode);
}

/// The converter with `en` held low: no start, the supervisor's mode is `Off` throughout.
module Idle() {
    signal en: Bit = false;
    signal sp_wr: Bit = false;
    signal sp_data: Bit = 0;
    signal load_step: Bit = false;
    signal inject: Bit = false;
    signal pgood: Bit;
    signal fault: Bit;
    signal mode: Bit;
    pub let buck = Buck(en, sp_wr, sp_data, load_step, inject, pgood, fault, mode);
}

The first time, the command compiles the converter, which takes a while, and says so on the error output. Then it simulates 600 µs of a circuit switching at 500 kHz with a 200 MHz clock, a couple of minutes on a laptop. The table has two rows: the first multiple of print_step at or after the first kept step is 599.5 µs, then 600 µs. The reference is 128, the code of 0.8 V; the mode is 2, regulation, after off and soft start; and the output sits within 3 mV of 0.8 V.

There are no record lines, yet the converter checks itself at every clock: its PWM carries a monitor that writes a checks record at every edge of the 200 MHz clock, saying the two power switches are never on together. Over the whole start that is more than a hundred thousand records, all passing, so the terminal hides them. piperine test runs both runs of the package and counts every one of them; --records startup.jsonl keeps them in a file.

Piperine is a set of Rust crates, each with one job. Your source goes down through them in a straight line, from text to numbers, and no crate knows about the ones above it: the solver never sees MSL, and the language never sees the solver. This chapter names the crates so that you know where a piece of behavior lives.

piperine-cliThe piperine command of chapter 16 and its seven commands. It reads the command line, calls piperine-api and lays out the text; every rule of what a run prints and judges lives in the library.
piperine-apiThe library a Rust program uses to drive Piperine, small on purpose: a Project found from its Piperine.toml, the runs it describes, a Session that compiles one run's top and runs its analysis, and the result as a table of values and the records your models emit. One more crate is in the tree and not built yet: a language server that will put the diagnostics of chapter 11 into your editor as you type. Until it is, piperine check gives the same diagnostics on the command line.

Three rules that hold it together

  • Each layer hands the next a finished model. The object model, the elaborated design, the plan and the device are each built once and not changed by the layer that reads them.
  • The device interface is the only door into the solver. Generated Rust, the interpreter and any device you bring yourself meet the solver through the same calls.
  • The two sides of the solver never call each other. Everything that crosses between analog and digital is an event the owner of time carries.

Nature

    on clk.rise() { q <- d; }
    on rst_n.fall() || clk.rise() { q <- false; }

}

module M(a: Electrical, o: Electrical, in ctl: Bit) {
    let y = transition(level, 0.0, tr, tf);
