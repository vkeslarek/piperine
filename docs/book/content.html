Chapter 1

Welcome

MSL, the Piperine mixed-signal language, is a language for describing circuits that a simulator runs: analog, digital, and both at once. It looks and reads like Rust, and most of it is Rust. The spec puts it plainly: MSL is "similar to Rust and based on it, but it is not Rust" (§0.1).

This book is for people who want to write models and read other people's models. It explains the language through examples and keeps the rule numbers in brackets, so you can look a rule up in the specification when you need the exact wording. You do not need to read the spec first.

A first look

Here is a resistor. The module head lists its ports, the body lists its parameters, and an analog block says what current flows:

/// Ideal resistor.
module Resistor(p: Electrical, n: Electrical) {
    /// Resistance, in ohms.
    r: f64 where r > 0.0;
    tc1: f64 = 0.0;
    tnom: f64 = 300.15 where tnom > 0.0;
}

analog for Resistor {
    i(p, n) +> v(p, n) / (r * (1.0 + tc1 * (temperature() - tnom)));
}

And here is a digital inverter with a propagation delay. It has no behavior block at all: its one line is a definition that drives the output from the input, tpd seconds later.

module Inv(in a: Bit, out y: Bit) {
    tpd: f64 = 10p where tpd > 0.0;
    y = !a after tpd;
}

A few things are already visible. Ports have types that say what flows through them (Electrical for a node, Bit for a logic signal). Parameters are plain declarations with an optional default and an optional where check. Numbers can carry SI suffixes: 10p is 10 × 10−12 and is always an f64 (App. A.2).

Three ways to write

A model changes the world in exactly three ways, and each has its own operator (§0.6). Learn these three and you can read any MSL file.

=
definition

y = a & b; drives a digital carrier from an expression, recomputed whenever its inputs change. Written in a module body.

+>
contribution

i(p, n) +> x; adds x to the current (or voltage) of a branch, at every Newton iteration. Written in analog.

<-
commit

q <- d; schedules a new value for a digital carrier at the next microstep. Written in a reaction, on ev { … }.

Everything else writes nothing. let x = expr; only gives an expression a name. Nets are never "joined" by a statement: you pass the same carrier to two ports. Parameters have no assignment at all: models read them, and the host sets them.

What you get

One language covers the transistor-level analog model, the RTL-style digital block and the glue between them. A design is fixed at elaboration and then simulated by Piperine's native solver: DC, transient, AC and noise all come from the same source text (§11.1). Every outcome is a function of the source and of what the host does. There are no races (§0.1).

Testbenches, stimulus, sweeps and optimization do not live in MSL. They live in the host, a Rust or Python program that sets parameters, drives the top ports, runs analyses and reads the results (§23).

Status

The specification is complete. The front end that parses MSL and builds the object model (chapter 12) exists and is growing, and it parses and resolves the whole standard library and every gallery model (App. G.38). The compiler from MSL to the solver does not exist yet, so nothing is executed. This book describes the language as specified.

Chapter 2

If you know Rust

"Everything this specification does not state is Rust, edition 2024, value semantics" (§0.4). Expressions, statements, patterns, match, enums, structs, traits, generics, closures, paths, use and pub all work the way you expect. The spec only lists the differences.

What is new: eleven concepts

MSL adds eleven concepts on top of Rust's values. Each one has a single rule (§0.5):

The new keywords are few: module, nature, signal, on, out, flip and after. in and extern get a new use. analog and digital are keywords only in front of for (App. A.1).

Good to know

The word "module" always means a hardware module in MSL. Rust's mod is called a namespace module (§3.4.1).

What is left out

A model is fixed at elaboration, so anything that allocates, mutates through references or runs concurrently is gone. The full list is App. B.3.6 and §1 rule 2; these are the ones you will notice:

Chapter 3

Values and functions

A value is data with no time. Everything a model computes with is a value; what it connects to is a carrier (next chapter). This part of the language is Rust, so this chapter is short.

Types

KindTypesNotes
booleanbool
integeru1 … u128, i1 … i128Any width, even u3 or UInt<{A + 1}>. Arithmetic always wraps.
floatf16, f32, f64, f128IEEE 754. Analog code computes in f64.
string&'static strLiterals only. Never carried by a signal.
compositearrays, tuples, struct, enum, Option<T>As in Rust.

Integer arithmetic wraps modulo 2N in every build: there is no overflow panic (§1 rule 6). usize is u64 on every machine, so a result never depends on the computer running it. The prelude gives you the constants Q, K_B, EPS0, PI, E and inf.

Repr: values that can travel

Only a type that implements Repr can be carried by a signal. Repr lays a value out as a row of boolean levels. Primitives have it built in; your own types derive it:

#[derive(Repr, Clone, Copy, PartialEq)]
enum Phase { Liquid, Boiling, Vapor }

A derived struct puts its fields side by side, first field lowest. A derived enum lays out a tag, then the widest payload. One-hot or Gray encodings are a hand-written impl Repr (§2).

Known and unknown

Every level of every value is either known or unknown. This is how MSL models the x of digital logic, and it applies everywhere, to locals and function arguments too (§3.3). Unknown enters only through a carrier that has no initial value yet, the literal Unknown, or a failed decode. Logic operators work level by level, so unknown & false is false and unknown | true is true.

The analog solver computes with real numbers only, so an analog block must say what an unknown means electrically. It reads a digital carrier through known(), known_or(d) or, for a Bit, high():

module SampleHold(vin: Electrical, vout: Electrical, in clk: Bit) { signal held: Bit = 0.0; }
digital for SampleHold { on clk.rise() { held <- v(vin); } }
analog for SampleHold { v(vout) +> held.known_or(0.0); }

Writing v(vout) +> held; instead is error E0150, and the diagnostic names the carrier. "The model says what an unknown means electrically; the language does not guess" (§3.3.5).

Functions

A function is computation without time. It keeps no state, writes no carrier and places no instance (§3).

pub fn diode_current(vd: f64, is: f64, nvt: f64) -> f64 { is * ((vd / nvt).exp() - 1.0) }
pub fn handshake(req: Bit, ack: Bit) -> Event { req.rise() && ack }
#[derivative(erfcx_dx)] extern "C" fn erfcx(x: f64) -> f64;

You never declare where a function may be called. The compiler infers a class from the body: a pure function works anywhere; one that probes a voltage or reads now() works where the solver is running; one that returns Event works where events go. Inside analog, calls are differentiated automatically. An extern "C" function used there needs #[derivative(...)], naming one derivative per f64 argument.

Good to know

Anything with state is a module, never a function. fn f(x: f64) -> f64 { ddt(x) } is an error; write module f(x: f64) -> f64 { ddt(x) } (§3 rule 4). Chapter 5 shows modules that return values.

Optional parameters

There are no default arguments and no overloading. Trailing parameters of type Option<T> may be left out, or passed by name to skip earlier ones (§3.2). Passing a plain T wraps it in Some, the one implicit conversion in the language:

cross(e)                    // rising, simulator tolerances
cross(e, 1p)                // with ttol
cross(e, etol: 1u)          // skips ttol
idt(x)                      // an integrator, no initial condition, no reset
idt(x, 1.0, reset: rst)

Chapter 4

Natures and carriers

A carrier is something that exists over time: a wire, a node, a register. Every carrier has a nature, which says what it holds and what happens when several modules drive it (§4).

Natures

nature Bit { value: T }                              // prelude; Bit is Bit
nature Wire { value: Logic, resolve: Logic::wired }                  // stdlib (§22.3): strengths, high impedance
nature Electrical {
    potential: Voltage { access: v, units: "V", abstol: 1u },
    flow:      Current { access: i, units: "A", abstol: 1p },
}
nature Thermal {
    potential: Temperature { access: temp, units: "K", abstol: 1m },
    flow:      Power       { access: pwr,  units: "W", abstol: 1n },
}
nature VSignal { potential: Voltage { access: v, units: "V", abstol: 1u } }   // signal-flow

There are two families. A discrete nature declares value and is computed by the event engine. A continuous nature declares potential (and usually flow) and is computed by the analog solver.

The access names become the probes: v(a, b) reads a voltage and i(a, b) a current on Electrical; temp and pwr do the same on Thermal. Units are labels for people and are never checked. abstol is the solver tolerance for that quantity. There is no inheritance between natures; a high-voltage variant of Electrical is a second nature (§4 rule 5).

Signals

Inside a module, signal declares a carrier. An initial value is optional:

signal en:    Bit;                       // starts unknown
signal count: Bit = 0;
signal level: Bit = 0.0;            // real-number modeling: piecewise constant
signal lines: [Bit; 8];                  // eight carriers, each with its own events
signal bus:   Bit = logic("10xx");   // level by level; x is unknown
signal sda:   Wire;                      // resolved: any number of drivers
signal mid:   Electrical;                // internal node
signal vout:  Electrical = 0.0;          // where Newton starts

An array of carriers costs what you write into it: storage for an element exists from its first commit, so [Bit<u8>; 1 << 32] is fine (§5.1.3).

Ports

The port list decides what kind each port is, from its type (§8.1):

gnd is the reference node of every continuous nature. It is not a global net: a module reaches any other node only through its ports (§6 rule 1).

Bundles

A struct whose fields are all carriers is a bundle. Directions are written from the producer's side, and flip gives the consumer's view (§7). This register slice reads rx as a consumer and drives tx as a producer:

module Slice(in clk: Bit, rx: flip Stream, tx: Stream) {
    signal full: Bit = false;
    signal buf: Bit;
    tx.data = buf;
    tx.valid = full;
    rx.ready = !full || tx.ready;
}
digital for Slice {
    on rx.beat(clk) { buf <- rx.data; full <- true; }
    on clk.rise() && !(rx.valid && rx.ready) && tx.ready { full <- false; }
}

Analog and digital never touch directly

A Bit is never connected to an Electrical node, and no converter is ever inserted for you (§6.1). Between modules you place one explicitly: D2A, A2D or Bidir from the standard library. Inside one module, behavior crosses freely: analog reads digital carriers, and reactions probe voltages. Chapter 8 is about this.

Chapter 5

Modules and hierarchy

A module is ports, params and a netlist of signals and instances, fixed at elaboration. Its behavior over time lives in separate analog for and digital for blocks, in the same file (§8).

The body is a netlist

Body items can come in any order, and every name is visible in the whole body and in the module's blocks (§8.2):

ItemExample
paramc: f64 = 1p where c > 0.0;
signalsignal mid: Electrical;
instancelet r1 = Resistor(a, b) { r: 1k };
named expressionlet half = r / 2.0;
definitionbusy = st != Tx::Idle;
generationfor k in 0..N { … }, if cond { … }

A param without a default is required. One of type Option<T> may be left out. A where clause is a check over this param and earlier ones, for example n: f64 = 1.0 where (0.1..=10.0).contains(&n);. A param read by generation, an array length, a const generic argument or a template is structural: it is fixed at elaboration (§8.1.2).

Instances

An instance is placed by calling the module with connections, positionally in port order, then an optional param block. Here is a switched-capacitor integrator that is all structure (App. D.6):

module RSwitch(a: Electrical, b: Electrical, in ctl: Bit) { ron: f64 = 100.0; roff: f64 = 1G; }
analog for RSwitch { i(a, b) +> v(a, b) / if ctl.high() { ron } else { roff }; }

module OpAmpIdeal(inp: Electrical, inn: Electrical, vout: Electrical) { a0: f64 = 1e5; }
analog for OpAmpIdeal { v(vout) +> a0 * v(inp, inn); }

/// Non-overlapping two-phase clock: pure structure.
module TwoPhase(in clk: Bit, out phi1: Bit = false, out phi2: Bit = false) {
    gap: f64 = 50p;
    phi1 = clk after if clk { gap } else { 0.0 };      // rises gap after clk, falls with it
    phi2 = !clk after if clk { 0.0 } else { gap };     // the mirror
}

/// Stray-insensitive SC integrator: structure only.
module ScIntegrator(vin: Electrical, vout: Electrical, in clk: Bit) {
    cs: f64 = 1p; cf: f64 = 4p;
    signal phi1: Bit;
    signal phi2: Bit;
    signal x: Electrical;
    signal y: Electrical;
    signal vg: Electrical;
    let ck = TwoPhase(clk, phi1, phi2);
    let s1 = RSwitch(vin, x, phi1);
    let s2 = RSwitch(x, gnd, phi2);
    let s3 = RSwitch(y, gnd, phi1);
    let s4 = RSwitch(y, vg, phi2);
    let csmp = Capacitor(x, y) { c: cs };
    let cfb = Capacitor(vg, vout) { c: cf };
    let amp = OpAmpIdeal(gnd, vg, vout);
}

Notice ron: f64 = 100.0, not 100. An integer literal never becomes an f64 (§3.2.3), while an SI literal like 1G always is one.

A parent can reach into a child only through what the child marks pub. The SAR ADC of App. F.1 hangs its own capacitor on a public node of its DAC: analog for SarAdc { i(dac.core) +> ddt(cpar * v(dac.core)); }.

Modules that return a value

A module may take value inputs and end its body with a result, declared with -> T. Then you can call it inside an expression, and every call is an instance with its own state (§8.3). This is how every operator with memory works: ddt, idt, delay, cross, transition. The standard integrator is written in MSL itself:

pub module idt(x: f64, ic: Option, reset: Option) -> f64 {
    signal y: S;
    potential(y)                             // the result
}

analog for idt {
    let hold = reset.unwrap_or(false) || (ic.is_some() && analysis(Static));
    if hold { potential(y) +> ic.unwrap_or(0.0); } else { flow(y) +> ddt(potential(y)) - x; }
}

An instance may read its own result through a node, which is how you write a differential equation. This PI controller's integral reads itself (§8.3):

fn windup(u: f64, lo: f64, hi: f64) -> f64 { u.clamp(lo, hi) - u }

/// PI with output limits and back-calculation anti-windup: the integral reads its own result.
module PiAw(e: VSignal, y: VSignal) {
    kp: f64 = 0.5; ki: f64 = 2k; kt: f64 = 10k;
    lo: f64 = 0.0; hi: f64 = 1.0 where hi > lo;
    let xi = idt(ki * v(e) + kt * windup(kp * v(e) + xi, lo, hi));
}
analog for PiAw { v(y) +> (kp * v(e) + xi).clamp(lo, hi); }

Good to know

Every placement is one instance. let acc = idt(v(a)); names one integrator, and every read of acc is that same integrator. Two calls with equal arguments are two integrators (§8.3.3).

Templates: modules as values

A module with its params bound is a value, called a template: Name { params }. You can pass it as a param and place it later. That makes cells swappable (§8.4):

/// One-transistor one-capacitor DRAM cell; Cell is the bundle of §7.
module Dram1T1C(c: Cell) {
    cs: f64 = 30f;
    ron: f64 = 5k;
    rleak: f64 = 1T;
    pub signal sn: Electrical = 0.0;     // storage node
}

module MemoryBank(in wl: [Bit; ROWS], bl: [Electrical; COLS]) {
    cell: C;
    for r in 0..ROWS { for c in 0..COLS { pub let cells = cell(Cell { wl: wl[r], bl: bl[c] }); } }
}
let bank = MemoryBank::<_, 64, 32>(wl, bl) { cell: Dram1T1C { cs: 30f } };   // in a parent's body

The bound C: Fn(Cell) accepts any module whose ports are one Cell. A function can also return a template, which is how binning reads:

/// Binning: the function picks the params, the caller places the result.
pub fn nch(l: f64, w: f64) -> Bsim4 {
    let vth0 = if l < 0.18u { 0.42 } else if l < 1u { 0.45 } else { 0.47 };
    Bsim4 { l: l, w: w, vth0: vth0 }
}
let m1 = nch(0.13u, 2u)(d, g, s, b);

Generation, multiplicity and extern models

  • Generation. for and if over params and constants unroll at elaboration, in the body and in digital blocks. Each unrolled placement is an instance of its own.
  • m and dtemp. Every instance has these two implicit params. m makes it behave as m copies in parallel and multiplies down the hierarchy; dtemp offsets the temperature and adds up (§8.5).
  • Extern modules. A model compiled to OSDI, or another simulator by cosimulation, is declared with its ports and params and placed like any module:
#[link("bsim4.osdi", model = "bsim4")]
extern "osdi" module Bsim4(d: Electrical, g: Electrical, s: Electrical, b: Electrical) {
    l: f64 = 1u;
    w: f64 = 1u;
    vth0: f64 = 0.4;
}

Chapter 6

Analog behavior

An analog block is straight-line code that runs at every Newton iteration and remembers nothing between iterations. The past comes from instances such as ddt and idt, and from digital carriers (§11).

Contributions and probes

A branch is a pair of nodes. i(a, b) +> x; adds x to the branch's current. v(a, b) +> x; adds x to its voltage, which makes the branch a voltage source. Contributions add up, from anywhere in the module. Leave out the second node and it is gnd.

analog for Capacitor { i(p, n) +> ddt(c * v(p, n)); }
analog for Inductor  { v(p, n) +> ddt(l * i(p, n)); }

module Switch(a: Electrical, b: Electrical, in ctl: Bit) {}
analog for Switch {
    if ctl.high() { v(a, b) +> 0.0; } else { i(a, b) +> 0.0; }
}

The switch shows the one firm restriction. A branch may change between being a voltage branch and a current branch, but only on something that is constant during a solve: params, digital carriers, now(), analysis(Static). A choice that depends on a probe is an error (§11 rule 3, E0414). An if on a probe can still choose between expressions.

Everything is differentiated for you, through function calls, value inputs and results, so you never write a Jacobian (§11 rule 5).

A few more shapes

/// An equation is a row: a nature whose "flow" is the residual gives it the right tolerance.
nature Servo {
    potential: Voltage { access: v,   abstol: 1u },
    flow:      Voltage { access: err, abstol: 1u },
}

/// Ideal op-amp (nullor): drives vout so that v(inp, inn) == 0.
module Nullor(inp: Electrical, inn: Electrical, vout: Electrical) { signal x: Servo; }
analog for Nullor {
    err(x) +> v(inp, inn);  // the row of x carries the equation, tested against 1 µV
    v(vout) +> v(x);        // v(x) is the free unknown
}

/// Two coupled inductors: coupling is inside one module, which writes only its own branches.
module Coupled(p1: Electrical, n1: Electrical, p2: Electrical, n2: Electrical) {
    l1: f64; l2: f64; k: f64 where k.abs() <= 1.0;
    let mu = k * (l1 * l2).sqrt();
}
analog for Coupled {
    v(p1, n1) +> ddt(l1 * i(p1, n1) + mu * i(p2, n2));
    v(p2, n2) +> ddt(l2 * i(p2, n2) + mu * i(p1, n1));
}

One block, every analysis

You do not write separate DC and AC models. One analog block serves Dc, Transient, Ac and Noise (§11.1). analysis(Static) is true during an equilibrium solve, which lets a model hold a state at its initial condition there, as idt does above. For small-signal analyses the block is linearized around the operating point with ddt(x) read as jω·x:

A noise source is an instance of noise. Read one instance in two places and the two are fully correlated; two instances are independent (§11.1.8):

let n = noise(4.0 * K_B * temperature() / r, "thermal");
i(a, mid) +> n;
i(mid, b) +> -n;          // fully correlated

Walkthrough: the switched-capacitor integrator

Go back to ScIntegrator in chapter 5. It has no analog block of its own: all branches belong to its children. Here is what the solver sees (App. D.6).

  1. Operating point. Both clock phases start low, so all four switches are at roff and the capacitors carry no current. y and vg reach ground through s3 and s4; x sits at v(vin)/2 between s1 and s2. No node floats. That is what a finite roff buys.
  2. Sampling, phi1 high. x follows vin and y is grounded, so cs charges to v(vin), with a time constant of ron · cs = 0.1 ns per switch.
  3. Transfer, phi2 high. x is grounded and y joins the virtual ground vg. The charge cs · v(vin) moves onto cf.
  4. Per period. Charge is conserved at vg, so vout[n] = vout[n−1] + (cs/cf) · vin[n]: a non-inverting integrator with gain 0.25.
  5. Time points. Each phase edge changes a switch conductance that analog reads, so the solver lands exactly on all four edges per period. Capacitor charges stay continuous; only the currents step.
  6. DC and AC. DC solves the all-switches-off circuit above, not the sampled system. The AC sweep linearizes with both phases low. The sampled transfer function needs a periodic analysis (§16.3).

Chapter 7

Digital behavior

A digital block holds reactions. A reaction on ev { body } runs its body once, to completion, when the event ev fires. Inside it, q <- x; is a commit: it writes this module's drive of q, and the write applies at the next microstep (§12.1).

module Counter(in clk: Bit, out count: Bit = 0, out full: Bit = false) {}
digital for Counter {
    on clk.rise() {
        count <- count + 1;
        full  <- count == 254;      // reads the old count
    }
}

The rules of a microstep

  • Reads see the past. Every read sees the values at the start of the microstep. All the commits of a microstep apply together. That is why full above reads the old count, and why statement order inside a reaction rarely matters.
  • The last write wins. When two commits hit the same level in the same microstep, source order decides. All writers of one drive are in one module, so you can see the order in one file.
  • Modules never race. A one-driver carrier has one writer, and a resolved one combines its drives in a fixed order.
  • Delays are transport. q <- x after d; applies d seconds later. A new commit from the same statement removes that statement's pending commits due at or after it. p <- true; p <- false after w; is a pulse in either order.
  • A reaction never waits. There is no wait, no blocking write and no #0. A sequence over time is visible state, such as a counter.

Definitions and commits

A module drives a carrier in one of two ways, never both: with one = definition in the body, or with commits from its reactions (§5.2). Definitions describe combinational logic and delays; commits describe state. A set-reset latch needs no reaction at all:

/// Cross-coupled NOR gates with gate delay: pure structure.
module SrLatch(in s: Bit, in r: Bit, out q: Bit = false, out qn: Bit = true) {
    tpd: f64 = 10p where tpd > 0.0;
    q  = !(r | qn) after tpd;
    qn = !(s | q)  after tpd;
}

Without the after, the two definitions would form a loop through one-driver carriers, which is an elaboration error (§8.2.3, E0339).

above(e)like cross, and also at time 0 if e already starts above (stdlib)
every(t0, period), init()periodic times; the start (stdlib)
settleonce per time point, after the instant has gone quiet

Events combine with a || b (either fires) and ev && c, where c is a bool guard. A plain bool alone is not an event (E0430). Inside a reaction, an event used as a bool tells you whether it fired in this microstep:

/// Three-state phase detector: two events in one reaction, each tested as a bool.
module Pfd3(in fref: Bit, in fvco: Bit, out up: Bit, out dn: Bit) {
    signal state: Bit = 0;
    up = state == 1;
    dn = state == -1;
}
digital for Pfd3 {
    on fref.rise() || fvco.rise() {
        let mut s = state;
        if fref.rise() && s < 1 { s += 1; }    // which one fired?
        if fvco.rise() && s > -1 { s -= 1; }   // both at once: up first, then down
        state <- s;
    }
}

Many drivers: resolved nets

Open-drain lines, tristate buses and wired logic are not language features. They are a nature with a resolve function, from the standard library (§22.3). Any module that sees a Wire may drive it, and nobody counts drivers:

module IrqSource(in req: Bit, irq_n: Wire) { irq_n = if req { Logic::strong(false) } else { Logic::Z }; }

module IrqController(in clk: Bit, irq_n: Wire, out pending: Bit = false) {}
digital for IrqController { on clk.rise() { pending <- !irq_n.v; } }

module Board(in clk: Bit, in req0: Bit, in req1: Bit, out pending: Bit) {
    signal irq_n: Wire;
    let pu = Pullup(irq_n);                  // wins only while every source is released
    let s0 = IrqSource(req0, irq_n);
    let s1 = IrqSource(req1, irq_n);
    let ic = IrqController(clk, irq_n, pending);
}

Walkthrough: a flip-flop with async reset

module Dff(in clk: Bit, in rst_n: Bit, in d: Bit, out q: Bit) { reset: T; }
digital for Dff {
    on clk.rise() || rst_n.fall() { if !rst_n { q <- reset; } else { q <- d; } }
}
  1. Drives. Dff holds the one drive of q, by commits. q has no initial value, so it starts unknown.
  2. Events. If the clock rises and reset falls together, the reaction still runs once.
  3. Reset low from the start. The first value of rst_n is a change from unknown to low, so fall() fires at time 0 and q takes reset one microstep later.
  4. A clock edge. The reaction reads rst_n and d as settled in that microstep; the commit applies in the next.
  5. Unknown rst_n. Both arms run and their commits merge level by level, so q keeps the levels on which reset and d agree (§3.3.3). If you want Verilog's behavior instead, write if !rst_n.known_or(true).

Pipelines fall out of "reads see the past". One reaction can describe all three stages of a multiply-accumulate pipeline, in any statement order:

module MacPipe(in clk: Bit, in a: Bit, in b: Bit, in valid_in: Bit,
               out acc: Bit = 0, out valid_out: Bit = false) {
    signal a1: Bit;
    signal b1: Bit;
    signal v1: Bit = false;
    signal p2: Bit;
    signal v2: Bit = false;
}

digital for MacPipe {
    on clk.rise() {
        a1 <- a; b1 <- b; v1 <- valid_in;                    // stage 1
        p2 <- (a1 as i32) * (b1 as i32); v2 <- v1;           // stage 2
        if v2 { acc <- acc + p2 as i40; } valid_out <- v2;   // stage 3
    }
}

Chapter 8

Mixed-signal

Mixed-signal in MSL is not a separate sublanguage. One module can have an analog block and a digital block, and they share the module's names (§10). Two rules connect the worlds:

  • Analog reads digital through known_or, known or high(). A digital carrier is a constant of each solve. When it changes, the analog side sees a jump and is solved again (§15.2).
  • Digital reads analog by probing in a reaction, or by an event on an analog expression: above(v(vin) - vth). A crossing is located in time by the solver.

The instant

Time in MSL is a pair (t, n): a real time and a microstep. At one time, microsteps run until nothing is pending. The analog side is solved before the first microstep, and again after each one that changes something it reads (§0.5, §15).

flowchart LR
  A["solve analog
at time t"] --> B["microstep n
definitions settle,
reactions run"]
  B --> C{"commits changed
what analog reads?"}
  C -- yes --> J["jump: solve
analog again"]
  J --> B
  C -- "no, but commits pending" --> B
  C -- "quiet" --> S["settle reactions,
then next time point"]

A reaction that probes makes its instant a time point, so the solver lands on it exactly. A change to a digital carrier that analog does not read is not a jump: the analog solution is not recomputed for it.

A comparator

/// Comparator, right from the operating point: the event says which way it went.
module Comparator(inp: Electrical, inn: Electrical, out q: Bit = false) {
    ttol: f64 = 1p;
    let up = above(v(inp, inn), ttol);
    let dn = above(-v(inp, inn), ttol);
}
digital for Comparator { on up || dn { q <- up; } }

Between modules: converters

Across a module boundary, a Bit and an Electrical never connect. Place a converter from the standard library. A2D is a threshold with hysteresis; D2A drives a level through a resistance with finite edges; Bidir is a pad on a Wire (§22.4).

module A2D(a: Electrical, out d: Bit = false) { vth: f64 = 0.6; hyst: f64 = 50m; }
digital for A2D {
    on above(v(a) - vth - hyst / 2.0) { d <- true; }
    on above(vth - hyst / 2.0 - v(a)) { d <- false; }
}

Walkthrough: a first-order delta-sigma modulator

An integrator in continuous time, a one-bit quantizer sampled by a reaction, and feedback through a digital carrier (App. D.5):

module DeltaSigma1(vin: Electrical, in clk: Bit, out bit: Bit = false) {
    r: f64 = 100k; c: f64 = 1p; vref: f64 = 1.0;
    signal x: Electrical = 0.0;
}

analog for DeltaSigma1 {
    let fb = if bit.high() { vref } else { -vref };
    i(x) +> ddt(c * v(x)) - (v(vin) - fb) / r;
}

digital for DeltaSigma1 {
    on clk.rise() { bit <- v(x) > 0.0; }
}
  1. The equation. x has one branch, so KCL gives c · dv(x)/dt = (v(vin) − fb) / r.
  2. Start. In an equilibrium solve ddt is zero, so x has no DC path. Its = 0.0 holds it at 0 V through the transient's operating point. On the first step the hold is released, with no jump.
  3. A rising clock edge at (t, 0). The reaction probes, so t is a time point. It reads v(x) and commits bit.
  4. At (t, 1). If bit changed, analog reads the change: a jump. The capacitor charge stays; the feedback current steps by 2 · vref / r.
  5. Falling edges fire no reaction, and analog never reads clk, so they cost the solver nothing.
  6. DC, AC and noise. Outside a transient's operating point nothing is held, so a Dc solve is singular and names x. That is the truth about an integrator with no DC path. Ac and Noise fail the same way; the loop's response needs a periodic analysis (§16.3).

Bigger systems are just composition. The SAR ADC of App. F.1 places a SampleHold, a resistive DAC, the Comparator above and a binary-search reaction:

module SarAdc(vin: Electrical, in clk: Bit, in start: Bit, out code: Bit, out done: Bit) {
    cpar: f64 = 50f;
    signal vh: Electrical;
    signal vdac: Electrical;
    signal cmp: Bit;
    let sh = SampleHold(vin, vh, start);      // 12.1
    let dac = Dac8(code, vdac);
    let comp = Comparator(vh, vdac, cmp);    // 13
    let logic = SarLogic(clk, start, cmp, code, done);
}
analog for SarAdc { i(dac.core) +> ddt(cpar * v(dac.core)); }    // the parent's own branch on a public node

Good to know

App. D.7 condenses the guidance: read a digital carrier in analog only when the analog behavior depends on it; prefer known times (at, after) to crossings; sample at a clock edge with a reaction, not with cross on the clock's analog image; give edges a duration with transition when edge rate matters.

Chapter 9

Files, modules and packages

MSL organizes code the way Rust and Cargo do, without exceptions: files are namespaces, a tree of files is a crate, and a directory with a manifest is a package (§3.4–§3.6).

Status

Crates and packages (§3.5, §3.6) are implemented: the object model resolves names across crates, and piperine-project reads Piperine.toml, locates path and git dependencies and writes the lockfile.

A project on disk

adc/
├── Piperine.toml          the manifest
├── Piperine.lock          written for you: pinned git commits
└── src/
    ├── lib.msl            the crate root
    ├── frontend.msl       mod frontend;
    ├── logic/
    │   ├── mod.msl        mod logic;
    │   └── sar.msl        pub mod sar;  (in logic/mod.msl)
    └── data/
        └── diode_iv.tbl   read by include_str!

The crate root is always src/lib.msl, and sources end in .msl. mod name; loads name.msl or name/mod.msl below the declaring file, exactly like name.rs and name/mod.rs. Having neither, or both, is E0161 (§3.6.2).

Namespaces: mod, use, pub

// src/lib.msl
pub mod frontend;           // src/frontend.msl
pub mod logic;              // src/logic/mod.msl

use util::filters::Rc;      // `util` is a dependency named in Piperine.toml
use crate::logic::sar::SarLogic;

Paths, use, pub and pub use follow Rust. crate is the root of your crate, self and super are relative. From another crate, an item is visible only when it and every namespace on the way to it are pub (§3.5.8). One rule is MSL's own: a hardware module and all its behavior blocks must be in the same file (§3.4.3).

The manifest

[package]
name = "adc"
version = "0.1.0"
authors = ["Mixed-Signal Team"]
description = "A SAR ADC and its building blocks"

[dependencies]
util = { path = "../util" }
pdk  = { git = "https://example.com/acme/pdk.git", tag = "v1.4.0", version = "1.4" }

That is the whole format: [package] with name and version (required), authors and description (optional), and [dependencies]. Any other table or key is E0171 (§3.6.3).

A package name and a dependency name are identifiers: no hyphens, no keywords, never std. The key you write under [dependencies] is the name you use in paths, Rust 2018 style. There is no extern crate and no leading ::.

The lockfile

Piperine.lock sits beside the root manifest and records the commit each git dependency resolved to. While a dependency's URL and requested reference stay the same, that commit is used; an explicit update resolves again. A lockfile inside a dependency is ignored. Path dependencies are not recorded: their location pins them (§3.6.13).

version = 1

[[package]]
name = "pdk"
version = "1.4.0"
source = "git+https://example.com/acme/pdk.git?tag=v1.4.0"
commit = "3f1c9a0e5b7d2c4e8a6f1b0d9c3e7a5f2b8d4c61"

No search paths, no textual include, no macros

A crate reaches another crate only through a dependency named in its manifest. No implementation may find one through a search path, a registry or an environment variable (§3.6.12). There is no -I and no package registry (App. G.0). There is no textual include of source either: code is shared through mod and use, and the only ! forms are emit! and include_str!.

include_str! is for data. It is allowed only in a const initializer, its path is relative to the source file, and the file is read once, at elaboration. A run never opens a file (§20):

const IV:  [(f64, f64); 64] = parse_table(include_str!("diode_iv.tbl"));   // whitespace columns
const ROM: [u32; 1024]      = parse_hex(include_str!("boot.hex"));         // $readmemh format

module MeasuredDiode(a: Electrical, k: Electrical) {}
analog for MeasuredDiode { i(a, k) +> table_model(v(a, k), &IV, "3E"); }   // cubic, error outside

The standard library and the prelude

std is a crate that ships inside Piperine. Every crate depends on it, no manifest names it, and no dependency may be called std (§3.5.3). The prelude, the pub items of std::prelude, is implied in every file, which is why Bit, Electrical, idt and above need no use. A handful of core names need nothing at all: gnd, Nature, m, dtemp, str and the core primitives like ddt and cross (§3.4.2). Chapter 10 tours both.

When names collide

The first segment of a path is looked up in this order, and the first hit wins (§3.5.4):

  1. the enclosing blocks and declarations;
  2. the items and imports of the enclosing namespace;
  3. the dependency names of the crate;
  4. the prelude;
  5. the core names.

So in an ordinary path, a local item beats a dependency of the same name, silently. In a use, the same clash is an error, never a silent choice:

mod util;                  // a local namespace called util
use util::cells::Cell;     // E0163: the local `util` or the dependency `util`?

Only a name that can head a path clashes: a namespace, a type, a nature or a module, as in Rust. A local fn util or const util lives in the value namespace, so util::cells::Cell still reaches the crate.

Two ways out (§3.5.5): rename the dependency in the manifest, or name the local one through crate.

[dependencies]
utilx = { path = "../util", package = "util" }    # now `utilx::cells::Cell`
use crate::util::cells::Cell;   // the local namespace, unambiguous

Chapter 10

Core and standard library

Every name you write in a model comes from one of three places: your own files, the core, or the standard library. The core is what only the simulator can provide: reading a voltage, taking a time derivative, locating a crossing. Everything else, idt, transition, Wire, Setup, is ordinary source code written in the language, shipped as the crate std, and you can open it and read it. The specification keeps the core in §14 and the library in Part VII (§22); this chapter is the tour that tells you which is which.

Every error condition in the spec has one code, Eppnn, where pp is the part that owns the rule. E01xx belongs to Part I (values, files and packages), E04xx to Part IV (behavior), E09xx to the lexer, and so on. Look a code up and you land on the rule that explains it (§0.2).

Chapter 12

The object model

The Piperine Object Model, the POM, is the in-memory model of a set of MSL sources. One call turns source text into an immutable Design, and every later stage starts from it: a type checker, an elaborator, the simulator front end, an editor. It is the Rust library piperine_lang::pom, and it reads the way Java reflection does. You ask a module for its ports, a signal for the module it is declared in, an instance for the module it places.

The promise: it mirrors your source

The POM's navigability mirrors the source. What you read back from a Design is the structure the author wrote.

Modules, instances and hierarchy come back as you wrote them. A generation for stays one for, never unrolled; a let stays a let. Name resolution only adds links between nodes. Anything that needs another shape, such as flattening, is a separate artifact built from the design. You never have to reverse-engineer an elaborator to find your own module.

sources ──► parse ──► lower ──► resolve ──► index ──► Design
(text)      syntax    arenas    names,       reverse   (immutable,
            tree      of nodes  classes,     tables    Send + Sync,
                                members                serializable)

A short tour

Take the Front model of §0.7, a comparator with hysteresis that drives a flip-flop:

/// A comparator with hysteresis that drives a flip-flop.
module Front(vin: Electrical, in clk: Bit, out q: Bit) {
    vth: f64 = 0.6;
    hyst: f64 = 50m;
    signal above_th: Bit = false;        // state: a signal
    signal d: Bit;
    d = above_th;                        // structure: a combinational definition
}

digital for Front {
    on above(v(vin) - vth - hyst / 2.0) { above_th <- true; }    // an analog event
    on above(vth - hyst / 2.0 - v(vin)) { above_th <- false; }
    on clk.rise() { q <- d; }                                    // a digital event
}

With the design built, you ask it questions in Rust. These lines are from the POM's own tour:

// The structure is what was written, by name.
let front = design.module("Front").unwrap();
let ports: Vec<_> = front.ports().iter().map(|p| p.name().unwrap()).collect();
assert_eq!(ports, ["vin", "clk", "q"]);
assert_eq!(front.params().len(), 2);
assert_eq!(front.signals().len(), 2);

// A signal knows where it is declared.
let d = front.signal("d").unwrap();
assert_eq!(d.declared_in().unwrap().name(), Some("Front"));
assert_eq!(d.qualified_name(), "Front.d");

// The `above(..)` calls are instances of a module, and the behavior block belongs to `Front`.
assert_eq!(front.instances().len(), 2);
let block = &front.digital_blocks()[0];
let events: Vec<_> = block.reactions().iter().map(|r| r.event().text()).collect();
assert_eq!(events[2], "clk.rise()");

// Reverse queries: who writes `d`, and who writes `q`.
assert_eq!(d.writers().len(), 1);                        // the definition `d = above_th;`
assert_eq!(front.port("q").unwrap().writers().len(), 1); // the commit `q <- d;`

What it is and is not

  • Always builds. build() returns a Design however broken the input. Parse errors keep the recovered tree and go to diagnostics(), sorted by file, offset and code.
  • Lossless. Every file keeps its text and syntax tree, and the tree can be rebuilt from the POM alone, spans included.
  • A plain value. A Design is Clone, comparable with ==, Send + Sync and serializable to JSON.
  • No type checking, evaluation, elaboration or simulation. Constants and where clauses stay expressions; generics are not instantiated. The POM says what was written and what each name refers to.
  • No mutation. Edit the source and build again.

With packages, a design is built over a graph of crates, each kept as authored, and names resolve across crates by the rules of chapter 9.

The full reference, every handle and method with an example, lives in the repository at docs/pom/.
